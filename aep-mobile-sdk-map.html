What this section is

Not "how to implement the Mobile SDK". Every SDK reference is that already. This is how to own an implementation you cannot build yourself: how to hold your own with a developer you do not manage, read what they wrote, and find the fault when data does not arrive.

The reader is an analytics person who owns the implementation but not the app. They have shipped web tracking and never shipped an app. They will be handing work to a mobile developer in another team, and when it breaks they will be expected to say why.

The central teaching problem is that this reader arrives with the wrong mental model. They know context data variables passed to Analytics, which is the Mobile Services and AppMeasurement world. The Edge Network path is XDM. Moving them off contextdata thinking is what steps 1, 4 and 9 exist to do, and it is the same shift the Web SDK Migration world already teaches for web.

The one-spine decision, measured

Eleven of the fifteen steps are entirely platform-neutral. The schema, the datastream, the tag property, consent configuration, Assurance validation and most of the debugging happen in Adobe's interface and read identically for iOS and Android.

Only step 7 carries a real split — dependency installation and SDK registration. Steps 8, 9 and 12 need the same instruction shown in two languages, which is a code block each, not a second page. Step 2 describes both toolchains because that is its subject.

This is the evidence for one spine rather than two tracks. Two parallel sequences would have duplicated eleven steps to serve four.

Open questions, before Phase 2

1 · React Native and Flutter. Adobe ships plugins for both, and a large share of real apps are built that way. The one-spine decision covered iOS and Android; it did not cover cross-platform frameworks. Three options: ignore them entirely, add one KB article explaining that the plugins wrap the same native SDK, or add a sixteenth step. Recommendation: one KB article. It costs almost nothing and stops a whole class of reader bouncing on step 7.

2 · Which step gets written first. Phase 3 builds one step end to end as the pattern. Recommendation: step 7, because it carries the only major platform split. If the one-spine treatment works there it works everywhere; if it does not, better to know before fourteen other steps are written to a shape that fails.

3 · Sample app. No screenshots is settled, but code blocks still need to be real. Whether they come from a working sample app or are written against the documentation changes how much can be verified.

Deliberately absent

No screenshots, matching the procedure container. No critique of Experience League — Amit ruled that angle out; the objective is simply how to implement, not where Adobe's documentation falls short. No certification content. No CJA analysis: this section ends when data lands correctly in both destinations, and CJA Learning picks up from there.

Every product, extension and API name here is provisional until verified against Experience League during drafting. Adobe's mobile naming has moved more than once.
