In the old world, two functions did your sending: s.t() for page views and s.tl() for clicks, each firing its own beacon. The Web SDK replaces both with a single command, sendEvent, that carries the payload you just assembled to the Edge. In Launch this becomes a rule with two actions: one that fills your variable object, one that sends it. The entire art of this step is making those two happen in that order, because Launch will cheerfully fire the send before the variables are set if you let it.

⚠ Common mistake

Leaving rule Order at defaults, so a Send Event fires before the variables populate. The payload arrives missing half its data. Fix: variable rules low Order (1), terminal Send Event high Order (50); enable "Run rule components in sequence."

⚠ Kill the global s object

Any custom code referencing s.eVar1 / s.events throws once AppMeasurement is removed. Rewrite it to populate XDM - Global and dispatch via Send Event.

What survives from the old way, and what does not

Worth saying plainly, because it is the reassuring half of this migration. The rule survives. It still lives in the tag property, it still runs in the browser, it still reads your data layer, and you still write it. Everything you learned building rules for AppMeasurement transfers directly. What changes is the output: the rule fills a structured XDM object rather than setting s.eVar1 one line at a time.

That is worth knowing because it is not true everywhere. In a mobile app there is no page and no data layer, so there is nothing for a rule to read and the app itself has to supply every value. The web keeps the model you already have. If you also work on apps, Where XDM values come from in the Mobile SDK guide sets out that difference.

One page load, followed all the way through

Everything above is mechanism. This is a requirement followed from the sentence somebody says in a meeting to the point where it can be reported on in two products. The requirement: we need to know which page people are on, and which of our country sites they are using, and we need to count page views.

Three values, and they leave the rule together in one payload:

pageName → web.webPageDetails.name URL → web.webPageDetails.URL propertyId → _yourtenant.propertyId page view count → _experience.analytics.event1to100.event1.value

Then they part company. Each takes a different route to each product, and the routes are the lesson rather than the values.

Page name and URLAnalytics: become the Page dimension automatically, because they are in the mapping table the Full Extension already covers.
CJA: arrive in the dataset as those fields, used as they stand.
Property identifier
_yourtenant.propertyId		Analytics: not in the mapping table, so it arrives as context data named a.x._yourtenant.propertyId, and a processing rule assigns it to an eVar.
CJA: arrives as that field. No rule, no mapping.
Page view count
_experience.analytics.event1to100		Analytics: increments event1 automatically.
CJA: ignores it, because CJA counts the rows themselves.

Adobe Analytics needs all three mechanisms. CJA needs one. In CJA the field you sent is the field you report on. The rest of that column exists to translate your payload into the shape Analytics has always expected, which is exactly what the Full Extension was built to spare you.

⚠ Country is not on that list

Somebody always asks. Country is not sent by the page at all. Geolocation is derived at the Edge Network from the request, filling placeContext.geo.countryCode and the region, city and postcode beside it. It is switched on as geolocation enrichment on the datastream. The property identifier looks like the same kind of dimension and arrives from the opposite direction, because only one of the two was written into your payload.

Internal search, and the question that comes after it

The second requirement shows why the first mattered. Marketing wants to know what people search for on the site, and how many results came back. A term and a count: one dimension, one metric, neither of them automatic.

search term → _yourtenant.search.term result count → _yourtenant.search.resultCount search event → _experience.analytics.event1to100.event2.value

The term takes the middle route above: context data, a processing rule, an eVar for Analytics, and straight into the dataset for CJA. The count is the interesting one. CJA can total, average and segment resultCount as it stands, because a number in a dataset is already a metric. Adobe Analytics cannot, so the same number is written again into a numeric event. One value, read once from the data layer, shaped twice on the way out.

Now change your mind, and see what it costs

This is the test worth running on any specification before it is built. Marketing comes back wanting the result count grouped into ranges, so zero, one to five, and six or more can be compared.

In CJA, this afternoon. The raw number is in the dataset, so the ranges are a derived field defined on top of it. They apply to the data already collected as well as to tomorrow’s.

In Adobe Analytics, awkwardly. A processing rule can test the value already arriving and set a bucketed eVar from it. That works, within what a rule can express, and it applies only from the moment it is switched on.

And on the web, unlike in an app, the third case is cheap. If nobody had sent the count at all, you would add it to the data layer and to the XDM object, and publish the tag property. That is an afternoon. The same omission in a mobile app is a schema change, an app change and a release. That is the sharpest difference between the two worlds, and the reason app specifications have to be right the first time.
