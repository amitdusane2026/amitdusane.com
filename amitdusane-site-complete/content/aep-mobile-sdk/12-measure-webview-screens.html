This step applies only if a screen in the app is a web page inside a WebView. Many apps have three or four and nobody mentions them, because to the people who built them they are just screens.

Skip it if the answer is genuinely none. Do not skip it because nobody has asked.
Why?What is a WebView? ↗Why does it get its own ECID? ↗

First, decide which SDK measures what

The Mobile SDK lives in the app and measures the app. A WebView is a browser, and the Mobile SDK cannot see inside it.

The page inside can carry the Web SDK, exactly as your website does. So there are three arrangements, and picking the wrong one is expensive because the cost arrives late.

Mobile onlyRight when WebViews are incidental: a terms page, a help centre, anything nobody needs measured. Those screens are invisible in reporting, and that is an acceptable gap.
BothRight when WebView screens carry real behaviour, such as checkout. The rest of this step is about making that work.
Web mostlyRight for a genuinely hybrid app. The Mobile SDK still earns its place for lifecycle and installs, which no web page can see.

The problem, in one sentence

The ECID belongs to the app. A WebView is a browser, and a browser creates its own.

Leave them alone and one person becomes two: an app journey that ends nowhere, and a checkout that arrived from nowhere.

There is a second problem in the same place. Both sides can measure the same thing twice. The app fires an event when the WebView opens, the page fires its own on load, and one action produces two records. Reports quietly run high and nothing errors.

Hand the identity into the WebView

The fix is one call on the app side and nothing at all on the web side.

The app asks the SDK for its identity as a query string, then appends it to the address the WebView loads. The Web SDK on the page reads that parameter on arrival and adopts the identity instead of creating its own.

iOS · Swift

Identity.getUrlVariables { (urlVariables, error) in
    guard let vars = urlVariables else { return }
    let url = URL(string: "https://example.com/loyalty?" + vars)
    // load `url` in the WebView
}

Android · Kotlin

Identity.getUrlVariables { urlVariables ->
    val url = "https://example.com/loyalty?" + urlVariables
    webView.loadUrl(url)
}

React Native · JavaScript

import { Identity } from '@adobe/react-native-aepedgeidentity';

Identity.getUrlVariables().then(urlVariables => {
  const url = "https://example.com/loyalty?" + urlVariables;
  // load `url` in the WebView component
});

Flutter · Dart

import 'package:flutter_aepedgeidentity/flutter_aepedgeidentity.dart';

String urlVariables = await Identity.urlVariables;
String url = "https://example.com/loyalty?" + urlVariables;
// load `url` in the WebView widget

What comes back is a query string called adobe_mc, carrying the ECID as MCMID, your organisation as MCORGID, and a timestamp[6]. Append it to the address and stop.

Three details decide whether it works

Five minutesThe parameter expires. Fetch it immediately before the load, not at launch.
Every oneEach WebView is a fresh browser, so each one needs its own call.
One wayApp to web only. There is no path back, and none is needed, because the app’s ECID is the one both sides share.
Where this goes wrong

A developer calls getUrlVariables once at startup and stores the result, which is what anybody would do with a value that looks like a device identifier. Every WebView opened in the first five minutes joins correctly, and every one after that quietly does not. The implementation passes testing, because testing happens in the first five minutes, and the discrepancy that appears later has no obvious cause.

The web half

If the pages inside your WebViews already run the Web SDK, that side is finished and this step is the whole of the join. The web-side identity work is the same as Migrate identity (ECID) in the Web SDK Migration guide.

✓ Ready when

You can name which screens are web content rather than guessing. Where those screens carry real behaviour, the identity is handed into them immediately before each load, and you have watched one app journey and one WebView journey arrive under the same ECID.
