A web launch has a moment. The tag publishes, and from that second every visitor is on the new version. An app release has no such moment. It has a staged rollout that reaches one percent of users on the first day. It has a store review that may add days to the front of that. Then it has a tail of people who will not update for months, and a few who never will. So launch day starts a slow replacement rather than completing one. Every number you look at for the next quarter contains two populations at once.

2
Do Have the app released with the production Environment File ID. This is the same value that caused trouble at installation time, and it is worth checking twice rather than once.
3
Do Build a report broken down by app version on day one. Not later, when a number looks wrong and nobody can tell whether the cause is behaviour or adoption.

Two habits make the next quarter readable. Report on app version from the start, so a strange trend can be checked against adoption in one click rather than argued about. And when a number moves, ask whether the population moved before asking whether the users did.

Where this goes wrong

A metric climbs steadily for three weeks after release and is presented as an improvement. It is adoption. The new version reports something the old one never did, so the line rises exactly as fast as people update, and it flattens the moment the rollout completes. Presenting that as a result once is survivable. Building a target on it is not.

✓ Ready when

The production build is live with the production ID, Assurance shows healthy events from it, and a version breakdown exists before anybody asks for one. The implementation is finished. What has started is the far longer job of keeping it honest as the app changes around it.
