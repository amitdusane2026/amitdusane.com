This is the shortest step in the guide.

If the app was started with MobileCore.initialize, lifecycle tracking is already on. No call to add, no rule to build, no ticket to raise.

The work here is confirming that, and knowing what to do about the older apps where it is not true.
Why?What does lifecycle measure? ↗Why does backgrounding end a session? ↗Can it tell you where installs came from? ↗

Two events carry everything

Application Launch fires when the app comes to the foreground. Application Close fires when it leaves.

Session length is the gap between them. Installs and upgrades are flags on the first launch after each.

Every number a product team asks for in the first month comes out of those two events[4].

Backgrounding an app ends a session, and answering a call backgrounds it. So app sessions are shorter and more numerous than web visits by their nature, and comparing the two counts directly will mislead whoever does it.

Confirm it, or fix it
Two questions. The first one usually ends the step.
1
Ask Does the app call MobileCore.initialize? If yes, lifecycle is on and this step is finished.
2
Ask Does it call registerExtensions instead? Then lifecycle is manual, and the pair below has to be present.

The manual pair, for older apps only

Only needed where the app still uses the older registerExtensions startup. On React Native and Flutter the plugins start lifecycle along with the SDK, so unless the project is on an old enough version to need native startup, there is nothing here to add.

iOS · Swift

MobileCore.lifecycleStart(additionalContextData: nil)
MobileCore.lifecyclePause()

Android · Kotlin

override fun onResume() {
    super.onResume()
    MobileCore.lifecycleStart(null)
}
override fun onPause() {
    super.onPause()
    MobileCore.lifecyclePause()
}
Where this goes wrong

An app on the manual pair calls lifecycleStart in one screen and not the others. Sessions then begin only when a person happens to open that screen first. Launch counts come in low, and the numbers look plausible enough that nobody questions them for a quarter.

✓ Ready when

Launch and Close events appear when the app is foregrounded and backgrounded. If the app uses the modern startup call you will have changed nothing to get here, which is the correct outcome rather than a sign something was missed.
