There is one API for this and it takes one argument.

Everything the app reports beyond lifecycle goes through Edge.sendEvent carrying an ExperienceEvent, and an ExperienceEvent is XDM: the field names agreed in the schema, filled in with values.

No trackAction, no trackState, no context data bag.

Sending an event

The shape is the same on every platform, because the shape is the schema[5]. A developer writing this does not invent field names, which is the point of having done the schema first.

iOS · Swift

var xdmData: [String: Any] = [
    "eventType": "application.interaction",
    "appInteraction": [
        "name": "add_to_basket"
    ]
]
let event = ExperienceEvent(xdm: xdmData)
Edge.sendEvent(experienceEvent: event)

Android · Kotlin

val xdmData = mutableMapOf<String, Any>(
    "eventType" to "application.interaction",
    "appInteraction" to mapOf(
        "name" to "add_to_basket"
    )
)
val event = ExperienceEvent.Builder()
    .setXdmSchema(xdmData)
    .build()
Edge.sendEvent(event) { }

React Native · JavaScript

import { Edge, ExperienceEvent } from '@adobe/react-native-aepedge';

const xdmData = {
  "eventType": "application.interaction",
  "appInteraction": { "name": "add_to_basket" }
};
const event = new ExperienceEvent({ xdmData: xdmData });
Edge.sendEvent(event);

Flutter · Dart

import 'package:flutter_aepedge/flutter_aepedge.dart';

Map<String, dynamic> xdmData = {
  "eventType": "application.interaction",
  "appInteraction": {"name": "add_to_basket"}
};
final ExperienceEvent event = ExperienceEvent({"xdmData": xdmData});
await Edge.sendEvent(event);

Four languages, one shape. What a developer needs from you is the exact path and the exact value, written down.

How to specify one, so it cannot be guessed wrong
Four things. Leave any of them out and a developer will fill the gap for you.
1
Give The eventType string, exactly. application.interaction is not the same as application.Interaction.
2
Give The full field path from the schema, not a description of it. appInteraction.name, not “the interaction name field”.
3
Give The exact value, and say whether it is fixed or comes from the app. add_to_basket is fixed; a product ID is not.
4
Give Where in the app it fires, in words a developer can act on: after the basket call succeeds, not when the button is tapped.
Where this goes wrong

The event fires on the tap rather than on success. Every abandoned or failed action then counts as a completed one, the number runs consistently high, and it agrees with nothing in the order system. This is the most common specification failure in app tracking, and it is caused by a ticket that said “track add to basket” and stopped there.

One screen load, followed all the way through

Everything above is mechanism. This is a requirement, from the sentence somebody says in a meeting to the moment it can be reported on in two products.

The requirement: we need to know which screen people are on, which of our country apps they are using, and we need to count screen views.

Three values, fired on every screen.

var xdmData: [String: Any] = [
    "eventType": "web.webpagedetails.pageViews",
    "web": [ "webPageDetails": [ "name": "Search Results" ] ],
    "_yourtenant": [ "propertyId": "uk-ios" ],
    "_experience": [ "analytics": [
        "event1to100": [ "event1": [ "value": 1 ] ]
    ] ]
]

Replace _yourtenant with your own tenant prefix. That is where every custom field in your schema lives.

Now watch what happens to each of the three on the way out. They leave together and then part company.

Screen name
web.webPageDetails.name		Analytics: becomes the Page dimension automatically, because it is one of the paths the Analytics field group already maps. Nothing to configure.
CJA: arrives in the dataset as that field, used as it stands.
Property ID
_yourtenant.propertyId		Analytics: not in the mapping table, so it arrives as context data named a.x._yourtenant.propertyId, and a processing rule assigns it to an eVar.
CJA: arrives as that field. No rule, no mapping.
View count
_experience.analytics.event1to100		Analytics: increments event1 automatically.
CJA: ignores it, because CJA counts the rows themselves.

Adobe Analytics needs all three mechanisms. CJA needs one. In CJA the field you sent is the field you report on. The rest of that column exists to translate your payload into the shape Analytics has always expected.

Country is not on that list, deliberately

Somebody always asks. Country is not sent by the app at all. Geolocation comes from the request at the Edge Network, filling placeContext.geo.countryCode and the region, city and postcode beside it, and it is switched on as geolocation enrichment on the datastream. Two dimensions sit next to each other in a report. One arrives by ticking a setting; the other arrives only because a developer wrote it into the payload.

Internal search, and the question that comes after it

The second requirement shows why the first mattered. Marketing wants to know what people search for inside the app, and how many results they got.

A term and a count: one dimension and one metric, neither automatic.

var xdmData: [String: Any] = [
    "eventType": "application.interaction",
    "_yourtenant": [ "search": [
        "term": "waterproof jacket",
        "resultCount": 24
    ] ],
    "_experience": [ "analytics": [
        "event1to100": [ "event2": [ "value": 24 ] ]
    ] ]
]

The term takes the middle route from the table above: context data, a processing rule, an eVar for Analytics, and straight into the dataset for CJA.

The count is the interesting one. CJA can total, average and segment resultCount as it stands, because a number in a dataset is already a metric. Adobe Analytics cannot, so the same number is written again into a numeric event, which is what event2 is doing. One value, sent once, shaped twice.

Where this goes wrong

The term is specified and the result count is not, because nobody asks what a search with no results looks like. Six months later somebody wants to know how often people search and find nothing, which is the single most actionable thing internal search reports. The answer is a schema change, an app change and a release. The value was free on the day the event was designed.

Now change your mind, and see what it costs

This is the test worth running on any specification before it goes to a developer. Marketing comes back wanting the result count grouped into ranges, so zero, one to five, and six or more can be compared.

In CJA, this afternoon. The raw number is in the dataset, so the ranges are a derived field on top of it. They apply to data already collected as well as to tomorrow’s.

In Adobe Analytics, awkwardly. A processing rule can test the value already arriving and set a bucketed eVar from it. That works, within what a rule can express, and it applies only from the moment it is switched on.

And if nobody had sent the count at all, neither is possible. The answer would be a schema change, an app change and a release, and a wait of weeks before any of it is measurable.

That is the whole lesson of this step. What you send decides what you can change your mind about later, and the tag property cannot rescue a value the app never supplied.

✓ Ready when

Every event on your list from Decide what to track has an eventType, a field path, a value and a firing point written down. For any value on it you can say how it reaches Adobe Analytics: automatically, through a processing rule, or not at all. A developer can build from that document without asking you a question, which is the test of whether it is finished.
