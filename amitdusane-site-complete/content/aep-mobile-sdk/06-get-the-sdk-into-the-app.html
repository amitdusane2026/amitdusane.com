A ticket goes to the mobile team on a Tuesday: add the Adobe SDK. Three weeks later a build reaches the store with the SDK inside it, and nothing arrives anywhere.

Nobody was careless. The library was added, the project compiled, the release passed review. One string was left as the placeholder.

That string tells the SDK which Adobe property it belongs to. It is the Environment File ID, it comes from the tag property you just built, and handing it over precisely is most of what this step asks of you.
Before this step

This is the first step you cannot do alone, and the vocabulary changes here. If a compiled file, a dependency manager and a build are not things you could explain to somebody else, Mobile app basics is worth ten minutes first. The rest of this page then reads as instructions rather than as jargon.

Everything before this was yours. This is not.

Every step so far happened in a browser tab, on properties you control. None of it needed anyone else to act.

The SDK goes inside the app itself. A developer opens a project you cannot open, and ships a build you cannot ship.

What you still own is the specification. A vague one is what produces the silent build above.

What to give the developer
Three things, in one ticket, so that none of them is guessed.
1
Where Data Collection › Tags › your mobile property › Environments
Do Copy the Environment File ID for Development. Say in the ticket that it is the development one.
2
Do Name the extensions the app needs: Core, Edge, Edge Identity, Edge Consent, Lifecycle, Assurance. Anything else is a later ticket.
3
Do Say where the SDK is started. “Somewhere at startup” is not an instruction. The platform pages below say exactly where.

One call does the whole job

MobileCore.initialize registers every extension bundled with the app, and switches on lifecycle tracking at the same time. There is no list of classes to keep matched to the library list.

Older guides show registerExtensions with an array and a completion block. That form still works and most existing apps contain it, so expect to meet it. It is no longer the shorter path[2].

Now pick your platform

Installing the SDK is the one step where the four kinds of app genuinely differ. Different tools, different files, different commands. Everything after this step is the same work in a different language.

Open the page that matches the app. If you do not know which it is, the three questions in How mobile apps are actually built settle it in one conversation.

iOSSwift. Swift Package Manager or CocoaPods, then the app’s startup file.
AndroidKotlin. Gradle and the bill of materials, then the Application class.
React NativeJavaScript. npm or Yarn, and no native code at all on version 7 and later.
FlutterDart. pub, and no native code at all on version 5 and later.
Where this goes wrong

The production Environment File ID reaches a debug build. Every developer test, every simulator run and every QA pass then lands in the property your business is watching, and none of it can be separated out afterwards. Ask for the development ID by name, and confirm the value in the build before anybody tests against it.

✓ Ready when

The app compiles with the SDK in it, the development Environment File ID is the value in the build, and SDK logs appear at debug level on launch. Nothing is being tracked yet, and that is correct. The SDK is present and configured, which is all this step claims.
