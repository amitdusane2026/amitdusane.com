A ticket goes to the mobile team on a Tuesday: add the Adobe SDK. Three weeks later a build reaches the store with the SDK inside it, and nothing arrives anywhere. Nobody was careless. The dependency was added, the project compiled, and the release passed review. One string was left as the placeholder. That string tells the SDK which Adobe property it belongs to, and the ticket never said which value to use. It is the Environment File ID. It comes from the tag property you already built, and handing it over precisely is most of what this step asks of you.

Before this step

This is the first step you cannot do alone, and the vocabulary changes here. If a compiled binary, a dependency manager and a build are not things you could explain to somebody else, Mobile app basics is worth ten minutes first. The rest of this page will read as instructions rather than as jargon.

Everything before this step happened in a browser tab, on properties you control. None of it needed anyone else to act. This one is different. The SDK goes inside the application binary. A developer opens a project you cannot open, and ships a build you cannot ship. What you still own is the specification. A vague one is what produces the silent build above.

What to hand over
Three things, in one ticket, so that none of them is guessed.
1
Where Data Collection › Tags › your mobile property › Environments
Do Copy the Environment File ID for Development. Say in the ticket that it is the development one.
2
Do Name the extensions the app needs: Core, Edge, Edge Identity, Edge Consent, Lifecycle, Assurance. Anything else is added later, by another ticket.
3
Do Say where initialisation goes. “Somewhere at startup” is not an instruction: AppDelegate on iOS, the Application subclass on Android.

One call now does the whole job. MobileCore.initialize registers every extension bundled with the app. It also switches on lifecycle tracking by default. So there is no list of classes to keep in step with the dependency list. Older guides show registerExtensions with an array and a completion block. That form still works, and most existing apps contain it, so expect to meet it. It is no longer the shorter path.[2]

The code they add
iOS · Swift Package Manager, then AppDelegate
// Add each package in Xcode: File > Add Package Dependencies
//   https://github.com/adobe/aepsdk-core-ios
//   https://github.com/adobe/aepsdk-edge-ios
//   https://github.com/adobe/aepsdk-edgeidentity-ios
//   https://github.com/adobe/aepsdk-edgeconsent-ios
//   https://github.com/adobe/aepsdk-assurance-ios

import AEPCore
import AEPEdge
import AEPEdgeIdentity
import AEPEdgeConsent
import AEPLifecycle
import AEPAssurance

func application(_ application: UIApplication,
                 didFinishLaunchingWithOptions launchOptions:
                 [UIApplication.LaunchOptionsKey: Any]?) -> Bool {

    MobileCore.setLogLevel(.debug)
    MobileCore.initialize(appId: "YOUR_ENVIRONMENT_FILE_ID")

    return true
}
Android · Gradle, then the Application subclass
// build.gradle.kts (Module :app)
implementation(platform("com.adobe.marketing.mobile:sdk-bom:3.+"))
implementation("com.adobe.marketing.mobile:core")
implementation("com.adobe.marketing.mobile:edge")
implementation("com.adobe.marketing.mobile:edgeidentity")
implementation("com.adobe.marketing.mobile:edgeconsent")
implementation("com.adobe.marketing.mobile:lifecycle")
implementation("com.adobe.marketing.mobile:assurance")

// MainApplication.kt
class MainApplication : Application() {
    override fun onCreate() {
        super.onCreate()

        MobileCore.setLogLevel(LoggingMode.DEBUG)
        MobileCore.initialize(this, "YOUR_ENVIRONMENT_FILE_ID")
    }
}

The Android dependency block names no versions. That is the sdk-bom line doing its job. It pins one set of versions known to work together, and every extension below it inherits from that set. A developer who lists versions by hand will eventually pin two that disagree. That failure surfaces at build time rather than in your reports, which is the better place for it.

Where this goes wrong

The production Environment File ID reaches a debug build. Every developer test, every simulator run and every QA pass then lands in the property your business is watching. None of it can be separated out afterwards. Ask for the development ID by name. Confirm the value in the build before anybody tests against it.

✓ Ready when

The app compiles with the SDK in it. The development Environment File ID is the value in the build. SDK logs appear at debug level on launch. Nothing is being tracked yet, and that is correct. The SDK is present and configured, which is all this step claims.
