A React Native app is written once, in JavaScript, and produces both the iPhone and the Android app.

Adobe ships a set of plugins that wrap the same native SDK underneath. So everything on the Adobe side behaves exactly as it does for a native app, and your request is built once rather than twice.

The packages

Five packages, added with npm or Yarn, whichever the project already uses.

npm install @adobe/react-native-aepcore
npm install @adobe/react-native-aepedge
npm install @adobe/react-native-aepedgeidentity
npm install @adobe/react-native-aepedgeconsent
npm install @adobe/react-native-aepassurance

Lifecycle is inside the core package, so there is nothing separate to add.

✓ No native code, since version 7

This is the part worth knowing, because older guides and older colleagues will tell you otherwise. From version 7 of the React Native plugins there is no need to start the SDK in the native iOS or Android files. Everything happens in JavaScript. On version 6 and earlier a developer had to edit AppDelegate and the Application class as well, and that second half is exactly where implementations used to be half-finished.

Starting the SDK

import { MobileCore, LogLevel } from '@adobe/react-native-aepcore';

MobileCore.setLogLevel(LogLevel.DEBUG);
MobileCore.initializeWithAppId("YOUR_ENVIRONMENT_FILE_ID");

Put that where the app starts, before the first screen is drawn. An event fired before the SDK is ready may never be sent, and nothing reports that it was lost.

The one risk cross-platform adds

The plugins wrap the native SDK, and a wrapper can fall behind the thing it wraps. When Adobe ships something new, the native SDK gets it first and the plugins follow, usually within weeks.

In practice this rarely causes trouble. Everything this guide needs has been supported for years: sending events, identity, consent, lifecycle and Assurance.

It becomes a problem only when somebody wants a newer or unusual feature, and it becomes a problem late, after the schema is agreed. So ask one question at the start.

Where this goes wrong

The team is on version 6, where native startup was still required, and follows a guide written for version 7. The JavaScript call is added and the native half is not. The app builds, runs, and sends nothing, and the code looks complete to everybody reading it. Confirm the plugin version before anybody follows any instructions, including these.

✓ Ready when

The five packages are in package.json, the SDK is started in JavaScript with the development Environment File ID, and SDK logs appear at debug level when the app launches. Then continue at Turn on lifecycle.
