Sooner or later there is a meeting where the app team believes tracking works and the numbers say it does not, and neither side can prove anything.

On the web that argument lasts a minute, because somebody opens a console. In an app there is nothing to open.

What there is instead is a set of calls that ask the SDK for its own state. A developer can put those behind a hidden debug screen in an afternoon, and that screen is worth more to you than any dashboard.
Why?Why does it sometimes come back empty? ↗What should the ECID look like? ↗

The three questions worth asking

ECIDIs the SDK started at all? An ECID exists from first launch. No ECID means nothing else is worth checking.
IdentitiesIs your customer ID actually attached, on the namespace you agreed? This is the cross-channel question.
ConsentsWhat does the SDK believe it is allowed to do? An unexpected value here explains most cases of missing data.

Read them in that order. Each answer removes a different half of the problem, and skipping to the interesting one is how an afternoon goes into a fault the first call would have found.

Reading them

iOS · Swift

Identity.getExperienceCloudId { ecid, error in
    print("ECID: \(ecid ?? "none")")
}
Identity.getIdentities { identityMap, error in
    print("Identities: \(String(describing: identityMap))")
}
Consent.getConsents { consents, error in
    print("Consents: \(String(describing: consents))")
}

Android · Kotlin

Identity.getExperienceCloudId { ecid ->
    Log.d("Adobe", "ECID: $ecid")
}
Identity.getIdentities { identityMap ->
    Log.d("Adobe", "Identities: $identityMap")
}
Consent.getConsents { consents ->
    Log.d("Adobe", "Consents: $consents")
}

React Native · JavaScript

import { Identity } from '@adobe/react-native-aepedgeidentity';
import { Consent } from '@adobe/react-native-aepedgeconsent';

Identity.getExperienceCloudId().then(ecid => console.log("ECID: " + ecid));
Identity.getIdentities().then(ids => console.log(JSON.stringify(ids)));
Consent.getConsents().then(c => console.log(JSON.stringify(c)));

Flutter · Dart

import 'package:flutter_aepedgeidentity/flutter_aepedgeidentity.dart';
import 'package:flutter_aepedgeconsent/flutter_aepedgeconsent.dart';

String ecid = await Identity.experienceCloudId;
IdentityMap ids = await Identity.identities;
Map<String, dynamic> consents = await Consent.consents;

On iPhone and Android every one of these hands its answer to a callback rather than returning it, and on React Native and Flutter it returns a promise or a future you have to wait for.

That is not a style choice. The SDK may still be starting, and a value that does not exist yet cannot be returned on the spot. Code written as though these answer immediately will read an empty value, and it will do so only sometimes, which is the worst way for a fault to behave.

Where this goes wrong

The debug screen is built, the ECID shows, and everybody declares the implementation sound. The ECID proves the SDK started and nothing more. It is present on an app with no events, no consent and no customer ID. Treat it as the first of three checks rather than the whole of one.

✓ Ready when

A hidden debug screen shows all three values, and you have seen them on a real phone rather than in a screenshot. Ask for it early. It costs a developer an afternoon and it saves whole meetings later.
