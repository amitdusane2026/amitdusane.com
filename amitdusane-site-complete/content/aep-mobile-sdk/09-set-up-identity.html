The SDK generates an ECID on first launch and attaches it to everything, with no work from anybody. That is genuinely useful and it is also the source of the most persistent misunderstanding in mobile analytics. An ECID identifies an installation, not a human being. The same person on a phone and a laptop is two ECIDs. The same person after a reinstall is two ECIDs. Every question that begins “how many customers” runs into that, and the answer is to send an identifier of your own alongside it.

Send your own identifier
iOS · Swift
let identityMap = IdentityMap()
let item = IdentityItem(id: "cust-8842190",
                        authenticatedState: .authenticated,
                        primary: false)

identityMap.addItem(item: item, withNamespace: "CustomerID")
Identity.updateIdentities(with: identityMap)
Android · Kotlin
val item = IdentityItem("cust-8842190",
                        AuthenticatedState.AUTHENTICATED,
                        false)

val identityMap = IdentityMap()
identityMap.addItem(item, "CustomerID")
Identity.updateIdentities(identityMap)

Three parts of that need deciding by you rather than by a developer.[6] The namespace must be the same string the website sends, or the two channels never join. The identifier must be the one your business already uses, not one invented for analytics. The authenticated state is a real claim about whether this person proved who they are, and it should be accurate rather than always set to authenticated.

Where this goes wrong

The app sends a customer ID and the website sends the same value under a different namespace. Both implementations pass their own tests, both look correct in isolation, and the profiles never join. Agree the namespace once, in writing, before either side builds anything.

✓ Ready when

The ECID is present on every event, and a customer ID is sent on the same namespace the web implementation uses, at the moment a person signs in. Removing it on sign-out matters just as much, and is the half people forget.
