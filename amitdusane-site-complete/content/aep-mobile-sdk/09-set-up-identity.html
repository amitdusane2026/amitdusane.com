The SDK generates an ECID on first launch and attaches it to everything, with no work from anybody. That is genuinely useful and it is also the source of the most persistent misunderstanding in mobile analytics. An ECID identifies an installation, not a human being. The same person on a phone and a laptop is two ECIDs. The same person after a reinstall is two ECIDs. Every question that begins “how many customers” runs into that, and the answer is to send an identifier of your own alongside it.

Send your own identifier
iOS · Swift
let identityMap = IdentityMap()
let item = IdentityItem(id: "cust-8842190",
                        authenticatedState: .authenticated,
                        primary: false)

identityMap.addItem(item: item, withNamespace: "CustomerID")
Identity.updateIdentities(with: identityMap)
Android · Kotlin
val item = IdentityItem("cust-8842190",
                        AuthenticatedState.AUTHENTICATED,
                        false)

val identityMap = IdentityMap()
identityMap.addItem(item, "CustomerID")
Identity.updateIdentities(identityMap)

Three parts of that need deciding by you rather than by a developer.[6] The namespace must be the same string the website sends, or the two channels never join. The identifier must be the one your business already uses, not one invented for analytics. The authenticated state is a real claim about whether this person proved who they are, and it should be accurate rather than always set to authenticated.

Where this goes wrong

The app sends a customer ID and the website sends the same value under a different namespace. Both implementations pass their own tests, both look correct in isolation, and the profiles never join. Agree the namespace once, in writing, before either side builds anything.

Only if the app has WebViews

The rest of this step applies to every app. This part applies only when a WebView screen carries behaviour you need measured, such as checkout or a loyalty page. If you do not know whether it does, that question is settled in WebView and hybrid apps, and it is worth settling before you finish this step rather than after.

Here is the problem in one sentence. The ECID belongs to the app, a WebView is a browser, and a browser mints its own. Leave them alone and one person becomes two: an app journey that ends nowhere, and a checkout that arrived from nowhere. Joining them is one API call on the app side and nothing at all on the web side.

Hand the identity into the WebView
Call this immediately before loading the page, not at launch. The reason is underneath.
iOS · Swift
Identity.getUrlVariables { (urlVariables, error) in
    guard let vars = urlVariables else { return }
    let url = URL(string: "https://example.com/loyalty?" + vars)
    // load `url` in the WebView
}
Android · Kotlin
Identity.getUrlVariables { urlVariables ->
    val url = "https://example.com/loyalty?" + urlVariables
    webView.loadUrl(url)
}

What comes back is a query string called adobe_mc, carrying the ECID as MCMID, your organisation as MCORGID, and a timestamp.[6] Append it to the URL and stop. Nobody writes anything on the web side. The Web SDK reads the parameter on arrival and adopts that identity on its first Edge Network request, so the page and the app agree without being introduced.

Three facts decide whether it actually works, and the first is the one that catches people. The parameter expires after five minutes. Fetch it at app launch, cache it, and open the loyalty screen twenty minutes later, and the handoff is rejected and the page quietly mints its own ECID. That is why the call belongs immediately before the load. The second is version floors: Identity for Edge Network 1.1.0 or later in the app, and Web SDK 2.11.0 or later on the page. The third is direction. This travels one way only, from app to web. Adobe documents no path back, and none is needed, because the app’s ECID is the one both sides end up sharing.

Where this goes wrong

A developer calls getUrlVariables once at startup and stores the result, which is what anybody would do with a value that looks like a device identifier. Every WebView opened in the first five minutes joins correctly, and every one after that silently does not. The implementation passes testing, because testing happens in the first five minutes, and the discrepancy that shows up later has no obvious cause.

The web half of this is the same identity work covered in Migrate identity (ECID) in the Web SDK Migration guide. If the pages inside your WebViews are already running the Web SDK, that side is done and this step is the whole of the join.

✓ Ready when

The ECID is present on every event, and a customer ID is sent on the same namespace the web implementation uses, at the moment a person signs in. Removing it on sign-out matters just as much, and is the half people forget. If the app has WebViews carrying real behaviour, the identity is handed into them immediately before each load rather than once at launch.
