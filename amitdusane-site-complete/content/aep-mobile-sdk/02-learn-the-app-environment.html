Most implementations that go wrong go wrong here, and not for a technical reason. An analytics practitioner asks for something in language that makes sense on the web, a developer builds what was literally asked for, and neither notices the gap until data is missing weeks later. Nobody in that exchange lacked skill. They lacked a shared vocabulary. This step is the vocabulary, and it is the only step in the guide that configures nothing.
Why?What is a build, exactly? ↗Where does your job end? ↗

Start with the thing that has no web equivalent. An app is compiled. The code a developer writes is translated into a binary before anyone runs it, and once it is compiled you cannot open it and read it. There is no view-source, no console to paste into, no network tab. Every question you would answer yourself in a browser has to be answered another way, and that is what Assurance exists for.

The words they will use
Xcode · Android StudioThe two workshops. Xcode builds iOS apps in Swift; Android Studio builds Android apps in Kotlin. A developer usually lives in one.
Dependency managerHow outside code gets in. Swift Package Manager or CocoaPods on iOS, Gradle on Android. “Add the SDK” means adding a line here.
Debug buildThe version a developer runs while working. Verbose logging, no optimisation, never shipped.
Release buildWhat reaches the store. Optimised, quiet, and the only version your real numbers come from.
Simulator · emulatorA fake phone on a laptop. Proves your code runs. Proves nothing about real networks, real permissions or real battery behaviour.
TestFlight · internal trackHow a build reaches testers before the public. This is where you get to see data first.

One habit is worth forming now. When a developer says a thing is done, ask which build it is in and whether that build has reached the test track. “It is in the code” and “it is in a build you can test” are different states, and the gap between them is where most of the waiting in this project happens.

Where this goes wrong

Testing on a simulator and calling it verified. A simulator has no real network conditions, no app store install, and often no working advertising identifier. Lifecycle and install numbers measured there will not match what real devices report, and the difference is discovered later, in a report somebody is presenting.

✓ Ready when

You can name the two toolchains, say what a dependency manager does, and tell a debug build from a release build. You are on the test track, or you have asked. None of this is Adobe knowledge, and all of it decides whether the next six steps go smoothly.
