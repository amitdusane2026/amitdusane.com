An eVar is a slot. You can fill it with anything, rename it on Tuesday, and repurpose it in March, and nothing objects. XDM does not work like that. A schema is agreed before any data moves, and once a field has received data it cannot be removed or retyped. It can only be added to. That reads as a restriction. It stops reading that way the first time somebody in Customer Journey Analytics asks what a field means and gets one answer instead of four.

A schema is a class plus field groups. The class fixes what kind of thing you are describing, and for app behaviour that is always Experience Event: something that happened at a moment in time. Field groups are the reusable blocks of fields you assemble on top.

Build it
1
Where Data Collection › Schemas › Create schema
Do Choose the Experience Event class. Name the schema for the app, not for the project.
2
Do Add Consumer Experience Event, the standard group carrying the common fields, and AEP Mobile Lifecycle Details, which is where Lifecycle puts installs, upgrades, launches and session length.[9]
3
Do Add one field group of your own for the events you listed in Decide what to track. One group, named for the app, rather than a group per event.
4
Where Data Collection › Datasets › Create dataset from schema
Do Create the dataset. The schema describes the shape; the dataset is the table the data actually lands in.
Where this goes wrong

Fields named after today's screens. A field called checkoutStep3Viewed is accurate for one release and misleading after the next redesign, and it cannot be removed once it has taken data. Name fields for what a person did, never for where they were standing when they did it.

✓ Ready when

The schema exists, carries both standard field groups plus one of your own, and a dataset has been created from it. Nothing is sending data yet. What you have is the agreement everything downstream reads from.
