A mobile tag property looks like the web one and does a much smaller job.

On the web a property holds rules that run in the browser, read the page, and build what gets sent. Here it mostly holds configuration: which datastream to talk to, which extensions to switch on, and what each is set to. The app fetches that at launch.

There is a rules engine, and it is narrower than the web one in a way worth knowing before you go looking for it.

Build it
Still all in a browser. This is the last step before you need a developer.
1
Where Data Collection › Tags › New Property
Do Choose platform Mobile. A Web property cannot be used by an app, and the two cannot be converted.
2
Do Install four extensions: Adobe Experience Platform Edge Network, Identity for Edge Network, Consent for Edge Network, and AEP Assurance. Mobile Core is always present and needs no installing.
3
Do In the Edge Network extension, select the matching datastream for each environment: development against Development, staging against Staging, production against Production.
4
Do Publish a library to Development. Until something is published, the environment exists but serves nothing.

Edge Network will not work without Identity for Edge Network. Treat those two as one item rather than two choices. Consent is separate on purpose, because a consent decision has to be expressible before any event is sent. Assurance earns its place by being the only way to see inside a finished app, which nobody can open and inspect the way you can inspect a web page.

Where this goes wrong

The property is created as Web rather than Mobile. It offers a plausible-looking set of extensions, none of which an app can load. The mistake appears only when a developer reports that the SDK cannot find its configuration. A property’s platform is fixed when it is created, so the fix is a new property.

What the rules engine here can do

The property does carry rules. They are written in the same interface as the web ones, turned into JSON alongside the rest of the configuration, and downloaded by Mobile Core when the app starts.

Two actions matter for measurement.

Attach DataAdds values to an SDK event, and never overwrites. Where the rule and the event disagree, the event wins.
Modify DataThe stronger one. Can add, change or remove values on the event, overwriting where they conflict.

So the honest answer to whether you can change values without a release is yes, within one hard limit.

A rule can only act on an event the app already sends. It can decorate. It cannot originate.

It cannot invent an event the app never sends. It cannot read a data layer, because a mobile app has none. It cannot reach a value the app never put anywhere. Everything a rule works with has to already be in the event, in the SDK’s own state, or typed into the rule as a fixed value. What the tag property can change holds the full list on both sides of that line.

That limit is the whole difference from the web, and it is not a shortcoming. A browser rule can read the page because there is a page to read. An app has nothing equivalent, so the app itself has to supply the values.

Where this goes wrong

Somebody promises a stakeholder that a new value can be added in the tag property, because Launch does exactly that on the website every week. The rule gets built and fires against an event that carries nothing to attach. Nothing errors and nothing arrives, and the request actually needed a developer and a release all along, three weeks later than it needed to.

✓ Ready when

A Mobile property carries the four extensions, each environment points at its own datastream, and a library has been published to Development. The Development Environment File ID is now available under Environments, and that is the value a developer needs next.
