Two things happen on Android. A developer adds the libraries in a Gradle file, then starts the SDK in a class that runs before anything else.

There is a third thing that is easy to miss, and it fails in total silence.

The Gradle block

// build.gradle.kts (Module :app)
implementation(platform("com.adobe.marketing.mobile:sdk-bom:3.+"))
implementation("com.adobe.marketing.mobile:core")
implementation("com.adobe.marketing.mobile:edge")
implementation("com.adobe.marketing.mobile:edgeidentity")
implementation("com.adobe.marketing.mobile:edgeconsent")
implementation("com.adobe.marketing.mobile:lifecycle")
implementation("com.adobe.marketing.mobile:assurance")

Notice that none of those lines names a version. That is the sdk-bom line at the top doing its job: it pins one set of versions known to work together, and every library below it takes its version from that set.

A developer who lists versions manually will eventually pin two that disagree. That failure shows up at build time rather than in your reports, which is the better place for it.

Starting the SDK

One call registers every extension in the app and switches on lifecycle tracking.

// MainApplication.kt
class MainApplication : Application() {
    override fun onCreate() {
        super.onCreate()
        MobileCore.setLogLevel(LoggingMode.DEBUG)
        MobileCore.initialize(this, "YOUR_ENVIRONMENT_FILE_ID")
    }
}

The line in the manifest that decides everything

Writing that class is not enough. The manifest has to point at it, through an android:name attribute on the application element. Only then does Android use that class instead of its own default one.

Leave the attribute out and nothing complains. The class compiles. The code sits in the project where any reviewer can see it. Android quietly uses its default class, onCreate never runs, the SDK never starts, and not one event is ever sent.

There is no crash and no error, because from Android’s point of view nothing went wrong.

Where this goes wrong

A reviewer reads the change, sees the startup code exactly where it was asked for, and approves it. The line in the manifest was never added. Weeks later the report is empty and the code still looks correct to everybody who opens it. When no data arrives at all on Android, check that the manifest names the Application class before you check anything else.

Checking what is really in the build

At debug log level the SDK logs each extension as it registers, naming the class.

Ask a developer to launch the app and send you those lines, then count them against what you asked for in the ticket. It takes them ten seconds and it answers a question you would otherwise be guessing at.

✓ Ready when

The Gradle block carries the bill of materials line, the Application class starts the SDK with the development Environment File ID, the manifest names that class, and the extensions in the startup log match your list. Then continue at Turn on lifecycle.
