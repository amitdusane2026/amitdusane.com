On the web you can be wrong for twenty minutes. A rule fires on the wrong page. Somebody notices, you fix the tag, you publish. By lunchtime every visitor has the corrected version. Most analytics practitioners have built their working habits on that loop. A mobile app does not have it. Your tracking code ships inside a binary that a stranger downloads once and may never update. Everything difficult about mobile follows from that one fact. It is worth sitting with before any schema gets built.
New to the app side?

This guide assumes you know Adobe Analytics and does not assume you know how apps are built. If Gradle, Xcode, native and React Native are unfamiliar words, read Mobile app basics before starting. That is where most mobile implementations quietly go wrong: not in the SDK, but in a room where the analytics person and the app developer are each fluent in a language the other does not speak.

Four things change, and they compound.

One of the four deserves saying before the list, because it is the one that catches people who have done this on the web for years. On a website a rule in the tag property reads the page and assembles what gets sent, and that rule is yours. There is no page here, so there is nothing for a rule to read. The app supplies the values, and it supplies all of them. The tag property still matters and its job is narrower: it carries configuration, and rules that can decorate an event the app already fires. Where XDM values come from sets out the two routes a value can take, and What the tag property can change sets out the line between what you can alter this afternoon and what needs a release.

What is different, and what it costs you
DeploymentA tag publish reaches everyone in minutes. An app release needs a build, a store review, and then a user who chooses to update. Weeks, and never everyone.
VersionsEvery version you ever shipped is still running on somebody's phone, still sending data, still using the tracking you wrote a year ago.
The pageThere is no page load to hang a hit on. There are screens, and a lifecycle: launches, backgrounds, crashes, upgrades.
The payloadContext data variables are not the unit any more. XDM is, and the difference is not cosmetic.

The fourth row catches people, because it looks like a naming change. On the web you learned to think in context data. A flat bag of keys, sent with a hit, mapped to eVars and props by processing rules. That model belongs to AppMeasurement and to the older mobile SDK. The Edge Network path takes XDM instead. XDM is a defined schema, with typed and nested fields, agreed before any data is sent.

The shortcut, and why to refuse it

An extension called Edge Bridge will take your existing trackAction and trackState calls, context data and all, and forward them to Analytics over the Edge. No schema work. For a team migrating a large app, that is a genuine rescue. For a new implementation it is a trap.[23] It produces data shaped for Adobe Analytics and poorly shaped for Customer Journey Analytics, which is usually the reason the work was funded. Build XDM.
