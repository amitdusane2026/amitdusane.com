On the web you can be wrong for twenty minutes. A rule fires on the wrong page, somebody notices, you fix the tag and publish. By lunchtime everyone has the corrected version.

A mobile app does not work that way. Your tracking code ships inside a file that a stranger downloads once and may never update. Everything difficult about mobile comes from that one fact.
New to the app side?

This guide assumes you know Adobe Analytics. It does not assume you know how apps are built. If Gradle, Xcode, native and React Native are unfamiliar words, read Mobile App Basics first. That is where most mobile implementations quietly go wrong: not in the SDK, but in a room where the analytics person and the developer each speak a language the other does not.

Four things change

DeploymentA tag publish reaches everyone in minutes. An app release needs a build, a store review, and then a person who chooses to update. Weeks, and never everyone.
VersionsEvery version you ever shipped is still running on somebody’s phone, still sending data, still using the tracking you wrote a year ago.
The pageThere is no page load to hang a hit on. There are screens, and a lifecycle: launches, backgrounds, crashes, upgrades.
The payloadContext data is not the unit any more. XDM is, and the difference is not cosmetic.

There is no page, so there is nothing for a rule to read

This is the one that catches people who have done this on the web for years.

On a website, a rule in the tag property reads the page and builds what gets sent. That rule is yours, and you can change it this afternoon.

An app has no page. So there is nothing for a rule to read, and the app itself has to supply every value.

The tag property still matters, and its job is narrower. It carries configuration, and rules that can decorate an event the app already sends. Where XDM values come from sets out the two routes a value can take. What the tag property can change sets out the line between what you can alter this afternoon and what needs a release.

XDM replaces context data

On the web you learned to think in context data: a flat bag of keys, sent with a hit, mapped to eVars and props by processing rules.

That model belongs to AppMeasurement and to the older mobile SDK. The Edge Network path takes XDM instead.

XDM is a defined schema with typed and nested fields, agreed before any data is sent. That sounds like more work at the start, and it is. It is also why a field means one thing rather than four.

The shortcut, and why to refuse it

An extension called Edge Bridge will take your existing trackAction and trackState calls, context data and all, and forward them to Analytics over the Edge. No schema work. For a team moving a large existing app, that is a genuine rescue. For a new implementation it is a trap[23]. It produces data shaped for Adobe Analytics and shaped badly for Customer Journey Analytics, which is usually the reason the work was funded. Build XDM.
