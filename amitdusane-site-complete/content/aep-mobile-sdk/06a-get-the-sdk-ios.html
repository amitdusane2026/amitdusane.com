Two things happen on iOS. A developer adds five packages in Xcode, then calls the SDK once when the app starts.

The second one is where this fails, because modern iOS apps do not all have the same startup file.

The packages

Swift Package Manager is Apple’s own tool and is built into Xcode. A developer adds each package by URL under File › Add Package Dependencies.

https://github.com/adobe/aepsdk-edge-ios
https://github.com/adobe/aepsdk-edgeidentity-ios
https://github.com/adobe/aepsdk-edgeconsent-ios
https://github.com/adobe/aepsdk-assurance-ios

Lifecycle comes inside the Core package, so there is no separate one to add.

An older project may use CocoaPods instead. That is fine and changes nothing about what you ask for. It changes the file the developer edits, from the Xcode interface to a text file called a Podfile.

Starting the SDK

One call does everything. It registers every extension in the app and switches on lifecycle tracking.

import AEPCore
import AEPEdge
import AEPEdgeIdentity
import AEPEdgeConsent
import AEPLifecycle
import AEPAssurance

func application(_ application: UIApplication,
                 didFinishLaunchingWithOptions launchOptions:
                 [UIApplication.LaunchOptionsKey: Any]?) -> Bool {
    MobileCore.setLogLevel(.debug)
    MobileCore.initialize(appId: "YOUR_ENVIRONMENT_FILE_ID")
    return true
}

Where that call goes, and why it is not one answer

For most of iOS history the answer was one file: AppDelegate, in the method that runs once the app has finished launching. Many production apps still work exactly that way.

An app built more recently with SwiftUI may have no AppDelegate at all. Its starting point is a small structure marked @main, and startup code goes in that structure or in an AppDelegate deliberately reattached.

Both arrangements are correct and both are common, so “put it at startup” does not point at a single file.

What you actually need is narrower and works either way: the SDK must finish starting before the first screen appears. An event fired before the SDK is ready may never be sent, and nothing reports that it was lost.

So ask whether the SDK starts before the first screen, rather than which file it sits in.

Where this goes wrong

A developer adds the packages to the main app target and the app compiles perfectly. The widget, the watch app and the internal staff build are separate targets, and the SDK is in none of them. Nobody notices until somebody asks why the widget has never reported anything. Say which targets need the SDK, by name, in the ticket.

✓ Ready when

The five packages are in the project, the initialise call carries the development Environment File ID, and SDK logs appear at debug level when the app launches. Then continue at Turn on lifecycle, which is mostly a step about confirming something you have already done.
