A rejection is the friendliest failure in this whole system, because unlike almost everything else on mobile, it tells you what is wrong.

XDM is validated. When a payload does not match the schema, the Edge refuses it and returns an error response, which appears in Assurance in place of the post-processed data you were expecting. The message names the field and the problem: a path that does not exist, a value of the wrong type, a required field absent.

Three causes account for most of them. A field was renamed in the schema after the app was built, so the app is sending a path that no longer exists. A type changed, and a value that used to be a string is arriving where a number is expected. Or the app is spelling the path differently from the schema, which is usually a capital letter.

All three are fixed on your side, except the last, and even that begins with you supplying the exact path rather than describing it. What matters is that a rejection is never a mystery: the answer is in the message.

For your implementation: read the error before forming a theory. It is genuinely quicker than reasoning about what might have changed, and the field it names is almost always exactly the field at fault.

⚑ Architect’s Decision

Never rename or retype a field in a live schema on the assumption that apps will catch up. Every already-installed version keeps sending the old shape, and each one of those events is rejected until its user updates.
