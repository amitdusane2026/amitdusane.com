A developer saying “it works on mine” is usually telling the truth about a build that nobody else will ever run.

Every project produces at least two kinds of build from the same source. A debug build keeps verbose logging, skips optimisation, and often points at test services. A release build is optimised, strips logging, and is signed for distribution. Only the release build reaches a store, so only the release build produces the numbers your business sees.

Most of the time the two behave identically, and that is exactly why the differences bite. Optimisation can change timing, which surfaces race conditions that never appeared in testing. Stripped logging removes the evidence a developer was relying on. And a debug build frequently carries the development Environment File ID, so it reports to a validation report suite while the release reports somewhere else entirely.

For your implementation: insist that final validation happens on a release build. Not a release-signed debug build, and not a build with logging left in. The point is to test the artefact that will actually ship.

⚑ Architect’s Decision

Sign nothing off from a debug build. Ask for a test-track release build and validate on that, because it is the last version identical to what a customer will install.
