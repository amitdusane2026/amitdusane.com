On the web, consent is a banner. In an app, consent is a default, and the banner is only how that default gets replaced.

A browser has a page already loading, and for a returning visitor a stored answer. An app on first launch has neither. Somebody has just downloaded it and opened it, and the SDK starts immediately, so events begin before anything has had a chance to ask a question.

The Consent extension holds a default that governs that window. There are three.

PendingHolds events in a queue and sends nothing. When the answer arrives the queue is either delivered or thrown away.
YesCollects from the first millisecond, before the question has been asked.
NoCollects nothing until told otherwise, so the first session is lost even from people who would have agreed.

Pending is the only one that neither collects before permission nor throws away the session of somebody who says yes.

It is a setting on the tag property rather than app code, so it changes without a release. That makes it one of the few genuinely reversible decisions in a mobile implementation.

For your implementation: set the default deliberately and have somebody with legal responsibility agree it. Then wire both answers rather than only the acceptance. An app that records agreement alone has implemented a button, not consent.

⚑ Architect’s Decision

Pending, unless instructed otherwise in writing. It is defensible in every market, and the queue means it costs you no data from the people who consent.
