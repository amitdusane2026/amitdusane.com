On the web, consent is a banner. In an app, consent is a default, and the banner is only how that default gets replaced.

A browser has a page already loading and, for a returning visitor, a stored answer. An app on first launch has neither. Somebody has just downloaded it and opened it, and the SDK initialises immediately, so events begin before any interface has had a chance to ask a question.

The Consent extension holds a default governing that window. Pending holds events in a queue and sends nothing until an answer arrives, at which point the queue is either delivered or discarded. Yes collects from the first millisecond. No collects nothing until told otherwise, so the first session is lost even from people who would have agreed.

Pending is the only one of the three that neither collects before permission nor throws away the session of somebody who says yes. It is a setting on the tag property rather than app code, so it changes without a release, which makes it one of the few genuinely reversible decisions in a mobile implementation.

For your implementation: set the default deliberately and have somebody with legal responsibility agree it. Then wire both answers rather than only the acceptance, because an app that records agreement alone has implemented a button rather than consent.

⚑ Architect’s Decision

Pending, unless instructed otherwise in writing. It is the defensible position in every market, and the queue means choosing it costs nothing in data from people who consent.
