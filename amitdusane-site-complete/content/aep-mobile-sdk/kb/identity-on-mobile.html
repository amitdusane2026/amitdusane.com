A cookie and an app identifier feel like the same idea until somebody asks how many customers you have.

The SDK creates an ECID on first launch and stores it in the app’s own storage on the phone. It survives launches, upgrades and restarts, and it is attached to every event without anybody arranging it. Within one installation it is completely reliable.

What it does not do is identify a person.

Delete the app and install it again and the storage goes with it, so the same human returns as a new ECID with no history. The same person on a phone and a tablet is two ECIDs that will never meet. The same person on your website is a third.

This is not a defect to be worked around. It is what a device identifier is, and every platform has been steadily tightening what can be known across installations rather than loosening it. Anything that promises to survive a reinstall is usually something you should not be doing.

For your implementation: use the ECID for what it is good at, which is joining one installation’s behaviour together. Send an identifier of your own for anything about people. Expect reinstalls to appear as new users, because that is what the data honestly says.

⚑ Architect’s Decision

Never answer a question about customers using ECID counts. If a stakeholder asks how many people use the app, the honest answer needs a signed-in identifier, and saying so early beats producing a number that quietly means installations.
