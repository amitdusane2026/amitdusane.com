It says nothing useful about installs, networks, permissions or the identifiers your reports depend on." slug: "simulator-vs-device" type: kb weight: 105 params: group: environment grouplabel: "The app environment" ---

A simulator is the app running on a laptop pretending to be a phone. The pretence is good enough for building and misleading for measuring.

What a simulator gets right is logic. If tracking code fires in the wrong place, a simulator will show you. What it gets wrong is everything the physical world contributes: a real network that drops, a real install from a store, real permission prompts, and in many cases the advertising identifier that attribution depends on.

Three things specifically will mislead you. Install metrics behave differently because a simulator install is not a store install. Queued events never queue, because the connection never fails, so you never see what happens when it does. And permission dialogs may not appear at all, which means consent flows can look complete when they have never been exercised.

For your implementation: use a simulator freely while tracking is being built, and validate nothing on it. The moment you are checking numbers rather than checking behaviour, move to a real device on a real connection.

⚑ Architect’s Decision

Simulator for building, real device for signing off. Anybody presenting simulator numbers as validation should be asked, gently, to install the app on a phone.
