The first tracking plan written for an app usually asks for several things the app is already reporting. That costs a sprint and produces nothing new.

The Lifecycle extension sends two events on its own: Application Launch when the app comes to the foreground, and Application Close when it leaves. They carry a standard field group called AEP Mobile Lifecycle Details.

From those two events you get:

InstallsThe first launch after installation.
UpgradesThe first launch after a version change.
LaunchesA count, every time the app comes to the foreground.
SessionsLength, measured as foreground time between the pair.
DeviceOperating system and app version, on every event.

Lifecycle is switched on by default when the SDK is started with the modern call, so on a correctly built app all of this arrives with no tracking code at all. Older apps using the explicit registration call start and pause lifecycle manually, and that is where the gaps appear.

For your implementation: read this list before writing a tracking plan, and delete from the plan anything already on it. That deletion is usually the largest single saving available in the first week.

⚑ Architect’s Decision

Take everything lifecycle gives you before asking for anything custom. A specification that repeats it is not more thorough, it is more expensive for the same result.
