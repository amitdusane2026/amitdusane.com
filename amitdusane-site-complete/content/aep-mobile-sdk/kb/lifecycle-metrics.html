The first tracking plan written for an app usually specifies several things the app is already reporting. That costs a sprint and produces nothing new.

The Lifecycle extension emits two events on its own. Application Launch when the app comes to the foreground, and Application Close when it leaves. They carry a standard field group called AEP Mobile Lifecycle Details, and between them they answer most of what a product team asks in the first month.

From those two events you get installs, identified as the first launch after installation. Upgrades, the first launch after a version change. Launch counts. Session length, measured as foreground time between the pair. And device, operating system and app version, on every event.

Automatic lifecycle tracking is switched on by default when the SDK is initialised with the modern initialiser, so on a correctly built app all of this arrives with no tracking code at all. Older apps using explicit extension registration call the lifecycle start and pause methods by hand, and that is where the gaps appear.

For your implementation: read this list before writing a tracking plan, and delete from the plan anything already on it. That deletion is usually the largest single saving available in the first week.

⚑ Architect’s Decision

Take everything lifecycle gives you before asking for anything custom. A specification that duplicates it is not more thorough, it is more expensive for the same result.
