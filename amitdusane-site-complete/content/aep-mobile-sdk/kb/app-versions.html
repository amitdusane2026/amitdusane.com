On the web there is one version of your tracking. In an app there are as many as you have ever released, all running at once.

People update at their own pace. A release reaches a fraction of users in its first week and most within a month. A stubborn remainder never update at all, and phones too old to run the newest build keep their last compatible version for good.

So the population sending you data is always a mixture, and the mixture shifts every day.

Two things follow. A tracking change is never fully deployed, so a field added this quarter is missing from part of your data for a long time afterwards, and that gap is not a fault. And any trend that spans a release contains two different implementations, so a metric can move because behaviour changed or because adoption did.

Telling those apart is easy if you prepared and awkward if you did not. App version arrives on every event from Lifecycle without anybody asking, so the breakdown is available from the first day.

For your implementation: build a version breakdown before you need one. Adding it while somebody is questioning a number is slower, and it looks worse, than having had it all along.

⚑ Architect’s Decision

Split by app version whenever a number moves near a release. Ask whether the population changed before asking whether the users did. Most surprising post-release trends are adoption in disguise.
