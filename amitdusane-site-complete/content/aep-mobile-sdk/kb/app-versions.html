On the web there is one version of your tracking. In an app there are as many as you have ever released, all running at once.

People update at their own pace. A release reaches a fraction of users in its first week, most within a month, and a stubborn remainder never. Devices too old to run the newest build hold their last compatible version indefinitely. So the population sending you data is always a mixture, and the mixture shifts every day.

Two things follow. A tracking change is never fully deployed, so a field added this quarter is absent from a slice of your data for a long time afterwards, and that absence is not a fault. And any trend spanning a release contains two different implementations, which means a metric can move because behaviour changed or because adoption did.

Telling those apart is easy if you prepared and awkward if you did not. App version arrives on every event from Lifecycle without anybody asking for it, so the breakdown is available from the first day.

For your implementation: build a version breakdown before you need one. Adding it while somebody is questioning a number is slower and looks worse than having had it all along.

⚑ Architect’s Decision

Segment by app version whenever a number moves near a release. Ask whether the population changed before asking whether the users did, because most surprising post-release trends are adoption wearing a disguise.
