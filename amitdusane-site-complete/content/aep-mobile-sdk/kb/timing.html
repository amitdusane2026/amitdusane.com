The worst faults on mobile are not the ones that break. They are the ones that work four times out of five.

The SDK starts in the background. Startup begins when the app launches and finishes a moment later, and during that moment the SDK exists but is not ready.

Code that asks it a question in that window gets an empty answer rather than an error. Nothing reports a failure. The value is simply missing.

Two situations produce it. Tracking calls fired very early, while the first screen is still being set up, may run before the SDK can send anything. And the calls that read the ECID, the identities or the consent state all hand their answers to a callback for exactly this reason. Code written as though they answer immediately reads whatever was there before the answer arrived, which is usually nothing.

Because it depends on how fast a phone starts, it appears on slow phones and cold launches and disappears on a developer’s machine. That is the tell: a fault only some people can reproduce, and never the person investigating it.

For your implementation: when a value is missing sometimes rather than always, suspect timing before suspecting configuration. Configuration fails consistently, which is a useful thing about it.

⚑ Architect’s Decision

Treat any intermittent tracking fault as a timing question until proved otherwise, and make sure every read of SDK state goes through its callback. Code that assumes an immediate answer will pass every test and fail in the field.
