The usual first move is to open the web tracking specification and translate it. That is the wrong move, and the result is easy to recognise: an app measured as though it were a slow website, full of screen views nobody analyses, missing the two or three things a product team actually argues about.

Mobile reports a great deal on its own. The events worth specifying are fewer than a web practitioner expects.

Start with what is free

The Lifecycle extension reports two events on its own: Application Launch and Application Close. They carry a standard field group called AEP Mobile Lifecycle Details.

Between them you get installs, upgrades, launch counts, session length and device detail. No tracking code and no ticket. Lifecycle is on by default when the SDK is started[4].

Time spent specifying what is already free is the most common waste in a mobile implementation, and it is usually the first week of one.

A screen is not a page view

However similar the two look in a report, they are not the same thing.

A web page has a URL, a referrer, and a load that ends. A screen can be pushed, popped, returned to, or kept alive in the background while somebody answers a call.

Count screens the way you count pages and you get session numbers nobody trusts. A screen is not a page view covers why the two never line up.

Decide the WebView question now

If any screen in the app is a web page inside a WebView, that screen may need the Web SDK rather than this one, and the two need a shared identity.

Settle it before the schema, not after. It is step 12, Measure WebView screens, and the reason it is worth asking about on day one is that the answer can change what you are building.

How to choose
Three questions, applied to every candidate event.
1
Ask Is Lifecycle already reporting this? If yes, it is finished. Move on.
2
Ask Would a decision change if this number moved? If nobody would act on it, it is not worth a release.
3
Ask Can it be described without naming a screen? Events that survive a redesign are worth more than events tied to today’s interface.
Where this goes wrong

The full web specification is handed over on day one, sixty events long. The developer estimates it honestly, the number frightens everybody, and the project stalls before the first release. A short list that ships beats a complete one that does not. Adding an event later is ordinary work.

✓ Ready when

You have a written list, short enough to read aloud, of the events the app will send beyond Lifecycle. Every one survives the three questions above. That list is what the XDM schema is built from, so it is worth getting right while it is still only a list.
