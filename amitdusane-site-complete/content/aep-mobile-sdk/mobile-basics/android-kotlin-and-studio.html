Android developers work in a tool called Android Studio and write in a language called Kotlin. Every Android app also has a file called the manifest, which confuses people more than the rest of Android put together.

Before you start

This page will not teach you to build mobile apps. It teaches you enough of the mobile world to understand what a developer is saying, to answer questions in a meeting when no developer is there, and to tell a developer exactly what you need and where it has to change. Words like Xcode, Gradle, native, Flutter and WebView are used here on purpose. You will hear them in every meeting.

Android Studio, and a build file you can read

Android Studio is Google’s development tool. It plays the same role Xcode plays on iPhone: code is written there, builds are run there, and the app is signed and uploaded from there.

One difference works in your favour. On iPhone the build settings sit inside the project and are usually edited through the interface. On Android they sit in Gradle files. Gradle is the build system, and its files are plain text, stored with the code, and readable by anybody.

So an Android developer can paste you the exact block that adds the Adobe SDK, and you can read it without opening anything. The list of libraries, the version numbers and the build variants are all text. Ask for that block by name and you will usually get it in the reply rather than in a meeting.

Kotlin, and two things you will see everywhere

The language is Kotlin. Google made it the preferred language for Android in 2019, replacing Java. Java has not disappeared. Any app with a few years behind it contains both, and developers move between them easily.

You will see two things in almost every line you are shown.

val and var. A val is set once and never changes. A var can change later. So if you see val, the value is fixed.

A question mark after a type. String? means the text might be missing, and Kotlin then forces the developer to say what happens when it is missing. You will see question marks on identity values and consent values, because those really can be missing while the SDK is still starting up.

The manifest is not one file

Every Android app has a file called AndroidManifest.xml. It is the app’s description of itself. It names the screens, the services, the permissions the app asks the phone for, and the class that runs first when the app starts.

Here is the part that confuses people. The manifest in the developer’s project is not the finished one.

Every library the app uses ships a small manifest of its own. At build time, Gradle merges all of them into a single document. That merged document is what goes into the app and what the phone reads. It has never existed as a file anybody typed.

So a library can declare a permission, register a service, or add a component without anybody on the app team writing a line.

The permission list a privacy review wants

Now the common problem makes sense. A privacy team asks for the complete list of permissions the app requests. The developer sends the manifest from the project. That file says nothing about the internet, and the app plainly uses the internet.

Both of those are true. The internet permission arrives from a library during the merge.

The Adobe SDK does exactly that. Its Core library declares android.permission.INTERNET and android.permission.ACCESS_NETWORK_STATE in its own manifest. Nobody typed either of them. Both arrive through the merge, and both are correct. The SDK has to reach the network, and it checks the connection before deciding whether to queue an event or send it.

✓ Ask for the merged manifest

Android Studio can produce the merged manifest, and that is the file to give them. The file in the project is a partial answer and will understate what the app requests. When a legal or privacy team asks what permissions an app uses, ask the developer for the merged manifest by that name. It takes a few seconds and it is the only version that matches what a phone receives.

How the SDK finds its own extensions

One line starts the whole SDK, and it names no extensions at all.

MobileCore.initialize(this, "YOUR_ENVIRONMENT_FILE_ID")

The manifest merge is what makes that possible. Each Adobe library registers the same small service in its own manifest, and attaches a note naming its own extension class. Once merged, that one service carries a list of every Adobe extension in the app. On startup the SDK reads the list and loads each class it finds.

This removes a whole category of mistake. The set of active extensions is exactly the set of libraries. Adding a library registers it. Removing a library unregisters it. There is no second list anywhere that can disagree with the first, which is what used to go wrong when extensions were listed manually.

It also gives you a fast way to check what is really in a build. At debug log level the SDK writes one line for each extension it finds, reading Discovered extension: and then a class name. Ask a developer to launch the app and send you those lines, then count them against what you asked for in the ticket.

Build type, flavour and variant

Android splits the same job iPhone gives to schemes and configurations, and it uses two words for it.

Build typeDebug or release. Decides logging, optimisation and very often which Adobe property receives the data.
FlavourOptional. Genuinely different editions from one set of code, such as one per brand. Many apps have none.
VariantThe two combined, and the precise answer to “which app am I looking at”. Ask for it by name.

A variant name is the two words joined together, such as freeDebug or brandaRelease. Where a project has flavours, the Environment File ID is very often set per variant, so each brand reports to its own property.

Asking which variant produced a build is the Android version of asking which scheme and configuration. It is the question that resolves test data appearing in a production report, and it usually resolves it in one reply.

Where startup lives, and the silence when it is missing

Android has one conventional place for code that must run before anything else. A developer writes a class that extends Application and puts startup work in its onCreate method. Starting the Adobe SDK belongs there, and that is what Get the SDK into the app asks for.

There is a second half that is easy to miss. Writing the class is not enough. The manifest has to point at it, through an android:name attribute. Only then does Android use that class instead of its own default one.

Leave the attribute out and nothing complains. The class compiles. The code sits in the project where anybody reviewing it can see it. Android quietly uses its default class instead, onCreate never runs, the SDK is never started, and not one event is ever sent. There is no crash and no error, because from Android’s point of view nothing went wrong.

Where this goes wrong

A reviewer reads the change, sees the startup code exactly where it was asked for, and approves it. The line in the manifest was never added. Weeks later the report is empty and the code still looks correct to everybody who opens it. When no data arrives at all on Android, check that the manifest names the Application class before you check anything else.

What to ask to see

Three requests cover this page. None needs a meeting, and a developer can answer all three in about two minutes.

Three things to ask for
Send them together. Each one is a copy and paste at the other end.
1
Ask The merged manifest, not the project file, and confirmation that it names the Application class.
2
Ask Which build variant this is, and which Environment File ID that variant carries.
3
Ask The Discovered extension lines from a debug launch, so the list can be counted against the ticket.
✓ What you can now do

You can explain to a privacy reviewer why the permission list they were sent is incomplete, and name the file that is complete. You can give a developer an Environment File ID knowing which build will carry it. You can read a Gradle block and say which Adobe extensions the app contains. And when Android sends nothing at all, you have a first question worth asking that most people reach only after two weeks.
