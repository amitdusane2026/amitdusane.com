A privacy review asks for the complete list of permissions the app requests. The developer sends the manifest. It says nothing at all about the internet, and the app plainly uses the internet. Both of those things are true at once.

That contradiction is the best possible way into how an Android app is put together. The file the developer sent is real. It is simply not the whole document. An Android app's manifest is assembled at build time. The app contributes to it, and so does every library inside it. The version a phone sees has never existed as a file anybody typed.

Understanding that one mechanism does more than settle the privacy question. It explains how the Adobe SDK registers its own extensions. It explains why nobody had to add an internet permission. And it explains where a whole class of silent startup failure comes from. This page covers the tools, the language, and that manifest.

Android Studio, and a build file you can actually read

The workshop is Android Studio, Google's development tool, built on top of a long-standing Java environment called IntelliJ. It plays the same role Xcode plays on iOS. Code is written there, builds are run there, and the app is signed and uploaded from there.

One difference matters to you, and it works in your favour. On iOS the build settings live inside the project and are usually edited through the interface. On Android they live in Gradle files, which are plain text, checked into the repository, and readable by anybody. Gradle is the build system, and its files are themselves small programs rather than settings screens.

The practical effect is that an Android developer can paste you the exact block that adds the Adobe SDK, and you can read it without opening anything. The dependency list, the version pinning and the build variants are all text. Ask for that block by name and you will usually get it in the reply rather than in a meeting.

Kotlin, and enough of it to read a line

The language is Kotlin. Google made it the preferred language for Android in 2019, displacing Java, which had been the platform's language since the beginning. Java has not gone anywhere. Any app with a few years behind it contains both, and developers move between them without ceremony.

Two habits of the language will carry you through most of what you are shown. The first is the pair val and var. A val is set once and never changes. A var can be reassigned. Seeing which one a developer chose tells you whether a value is meant to move.

The second is the question mark. A type written as String? is a string that might be absent, and Kotlin then forces the code to say what happens when it is. This is why you will see so many question marks around identity values and consent values. Those are exactly the things that can legitimately be missing when the SDK has not finished starting up.

The manifest is not one file

Every Android app has an AndroidManifest.xml. It is the app's declaration of itself. It names the screens, the services, the permissions the app requests, and the class that runs first when the app starts.

What surprises people is that the app's own manifest is one contributor among many. Every library the project depends on ships a manifest fragment of its own. At build time Gradle merges them all into a single document, and that merged document is what goes into the app and what the operating system reads. A library can therefore declare a permission, register a service, or announce a component without anybody on the app team writing a line.

The Adobe SDK does exactly that. Its Core library declares android.permission.INTERNET and android.permission.ACCESS_NETWORK_STATE in its own manifest fragment. Neither one is ever added by hand. Both arrive through the merge and both are in the shipped app. Both are also entirely correct. The SDK has to reach the network, and it checks connectivity before deciding whether to queue an event or send it.

The document a privacy review actually wants

Android Studio can produce the merged manifest, and that is the file to hand over. The source file in the repository is a partial answer and will understate what the app requests. When a legal or privacy team asks what permissions an app uses, ask the developer for the merged manifest by that name. It takes them a few seconds and it is the only version that matches what a phone receives.

How the SDK finds its own extensions

One line starts the whole SDK, and it names no extensions at all.

MobileCore.initialize(this, "YOUR_ENVIRONMENT_FILE_ID")

The manifest merge is what makes that possible. Each Adobe library's manifest fragment registers the same small service and attaches a piece of metadata naming its own extension class. Once merged, that one service carries a list of every Adobe extension the app contains. On startup the SDK reads the list back and loads each class it finds.

The consequence is worth holding onto, because it removes a whole category of mistake. The set of active extensions is exactly the set of dependencies. Adding a library registers it. Removing a library unregisters it. No second list exists anywhere to drift out of step with the first. That drift is precisely what used to go wrong when extensions were named by hand.

It also gives you a fast way to check what is really in a build. At debug log level the SDK writes one line per extension it finds, each reading Discovered extension: followed by a class name. Ask a developer to launch the app and send you those lines. Counting them against what you asked for in the ticket takes a few seconds, and it answers a question you would otherwise be guessing at.

Build types and flavours, which are the same idea in Android words

Android splits the same job iOS gives to schemes and configurations, and it uses two words for it. A build type is debug or release, the same pair as everywhere else. A product flavour is an optional second axis, for genuinely different editions of one app. Free and paid, say, or one build per brand in a group that runs several.

Combining them gives a build variant, and the variant name is the two words run together, as in freeDebug or brandaRelease. Where a project has flavours, the Environment File ID is very often set per variant, so that each brand reports to its own property.

Asking which variant produced a build is therefore the Android form of asking which scheme and configuration. It is the question that resolves test data appearing in a production report, and it usually resolves it in a single reply.

Build typeDebug or release. Which one you have decides logging, optimisation and, very often, which Adobe property receives the data.
Product flavourOptional. Genuinely different editions from one codebase, such as one per brand. Many apps have none at all.
Build variantThe two combined, and the precise answer to “which app am I looking at”. Ask for it by name.

Where startup lives, and the silence when it is missing

Android has one conventional place for code that must run before anything else. A developer writes a class extending Application and puts startup work in its onCreate method. Initialising the Adobe SDK belongs there, and that is what the implementation step asks for.

There is a second half to it that is easy to miss. Writing the class is not enough. The manifest has to point at it, through an android:name attribute on the application element. Only then does Android use your class instead of its own default one.

Leave that attribute out and everything still works, in the sense that nothing complains. The class compiles. The code sits in the repository where anybody reviewing the pull request can see it. Android quietly uses its default Application instead, onCreate never runs, the SDK is never initialised, and not one event is ever sent. There is no crash and no error in the log, because from Android's point of view nothing went wrong.

Where this goes wrong

A reviewer reads the pull request, sees the initialisation code exactly where it was asked for, and approves it. The registration line in the manifest was never added. Weeks later the report is empty and the code still looks correct to everybody who opens it. When data does not arrive at all on Android, check that the manifest names the Application class before checking anything else. It costs one question and it is a more common cause than it has any right to be.

What to ask to see

Three requests cover this page. None needs a meeting, and a developer can answer all three from a laptop in about two minutes.

Three things to ask for
Send them together. Each one is a copy and paste at the other end.
1
Ask The merged manifest, not the source file, and confirmation that it names the Application class.
2
Ask Which build variant this is, and which Environment File ID that variant carries.
3
Ask The Discovered extension lines from a debug launch, so the list can be counted against the ticket.
✓ What you can now do

You can explain to a privacy reviewer why the permission list they were sent is incomplete, and name the document that is not. You can hand over an Environment File ID knowing which build will carry it, which is Get the SDK into the app. You can read a Gradle dependency block and say which Adobe extensions the app contains. You can ask which build variant produced the data in front of you. And when Android sends nothing at all, you have a first question worth asking that most people reach only after a fortnight.
