Somebody says the app is React Native, and the room nods. Half of them are nodding because they know what that means and half because they do not want to be the person who asks.

This is worth twenty minutes of your time, because cross-platform frameworks are now a large share of the apps you will meet, and because the honest answer to what changes for you is short and reassuring. Most of what you will read online about this is written for developers deciding which to use. You are not deciding. You are arriving after the decision and need to know what it means.

The problem they exist to solve

Apple and Google built two entirely separate worlds. An iPhone app is written in Swift, built in Apple's tool called Xcode, and follows Apple's rules. An Android app is written in Kotlin, built in Google's tool called Android Studio, and follows Google's. The two share almost nothing. A button, a list, a screen transition: each has to be built twice, by two people, who cannot read each other's work.

For a company that wants both, this is expensive in a way that compounds. Two teams. Two codebases. Two sets of bugs. Every feature specified once and built twice, which means every feature can be built subtly differently twice. And when the business asks for something on a deadline, the deadline is set by whichever team is slower.

Cross-platform frameworks are the response. Write the app once, in one language, and let the framework produce both. That is the entire pitch, and when it works it halves the most expensive part of building an app.

What React Native actually is

React Native comes from Meta, and its name is two ideas stuck together. React is a way of building interfaces that web developers have used for over a decade: you describe what a screen should look like, and the framework works out how to draw it and how to redraw it when something changes. Native is the promise that what gets drawn is not a web page pretending to be an app, but the phone's own real buttons, real lists and real keyboards.

So a React Native app is written in JavaScript or TypeScript, the same languages your website almost certainly uses, and it produces something a user cannot tell apart from a native app. That combination is why it spread: a company with web developers already on staff could build a mobile app without hiring two new teams.

Underneath, there are still two real apps. The framework carries a small piece of native code for each platform, and your JavaScript talks to it. That layer matters to you, and it is the whole of what changes, which the next section explains.

What Flutter actually is

Flutter comes from Google and takes a different route to the same place. It is written in a language called Dart, which is not a language you will meet anywhere else, and instead of using the phone's own buttons it draws every pixel itself.

That sounds like a disadvantage and mostly is not. Drawing everything means a Flutter app looks precisely the same on both platforms, which designers tend to like and which makes a brand consistent. It also means the app is not waiting for the framework to support a new native control, because it was never using native controls.

The trade is that a Flutter app can feel very slightly unlike the platform it is on, in ways most users never consciously notice. For your purposes Flutter and React Native behave almost identically, and everything below applies to both.

Why a team chose one

Almost always cost and staffing rather than technology. A company with web developers picks React Native because those people can start on Monday. A company starting fresh, or one that cares strongly about a consistent look, more often picks Flutter. Neither choice was made with analytics in mind, and neither is a problem for you.

The three things that change

Here is the part worth carrying into a meeting. Everything on the Adobe side is identical. The schema, the datastream, the tag property, the extensions, consent, identity, Assurance: none of them knows or cares how the app was built, because all of them sit on Adobe servers and receive events that look the same whatever produced them. Nothing in this guide changes on that side.

Three things change on the app side.

The language your tracking is written in. Not Swift or Kotlin but JavaScript, or Dart for Flutter. When you read a code sample in Adobe documentation, you will need the plugin version rather than the native one, and the method names are recognisable but not always identical.

How the SDK gets in. Native projects add dependencies through Swift Package Manager, CocoaPods or Gradle. A React Native project adds them through the JavaScript package manager, npm or Yarn, and a Flutter project through its own tool. Same idea, different command.

How many times each request lands. This one is in your favour. One codebase means one implementation, so an event fires from one place and cannot drift between iOS and Android. That entire class of discrepancy, the one where a number disagrees between platforms because two developers interpreted the same ticket differently, simply cannot happen.

The one real risk, and how to test for it

The plugins are wrappers around the native SDK, and a wrapper can trail what it wraps. When Adobe ships something new, the native SDK gets it first and the React Native and Flutter plugins follow, usually within weeks and occasionally longer.

In practice this almost never bites, because the things you need for an implementation like this one, sending events, identity, consent, lifecycle and Assurance, have been supported for years and are stable. It bites when somebody wants a newer or more specialised capability.

So there is one question worth asking at the start, and it costs nothing.

How to spot one without asking

You usually can, from things you already have access to. A repository whose files end in .js, .jsx or .ts and which contains a package.json is React Native. Files ending in .dart with a pubspec.yaml are Flutter. Two separate folders, one full of .swift files and one full of .kt, is native.

You do not need to read any of those files. Recognising the shape is enough, and being the analytics person who recognises it changes how the rest of the project treats you.

✓ What you can now do

Say what React Native and Flutter are in a sentence each, explain why a team would choose one, and state confidently that nothing on the Adobe side changes. Ask the one question that matters, about plugin version and feature support. And know that a single codebase quietly removes the most common source of iOS and Android disagreement in mobile reporting.
