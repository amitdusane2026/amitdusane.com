React Native and Flutter are the two ways of writing one app that runs on both phones. A large share of the apps you will meet are built this way, and the honest answer to what changes for you is short.

Before you start

This page will not teach you to build mobile apps. It teaches you enough of the mobile world to understand what a developer is saying, to answer questions in a meeting when no developer is there, and to tell a developer exactly what you need and where it has to change. Words like Xcode, Gradle, native, Flutter and WebView are used here on purpose. You will hear them in every meeting.

The problem they solve

An iPhone app is written in a language called Swift, in Apple’s tool, following Apple’s rules. An Android app is written in Kotlin, in Google’s tool, following Google’s rules. The two share almost nothing.

So a button has to be built twice. So does a list, a screen, and the animation between screens. Two people do that work, and neither of them can read the other’s code.

For a company that wants both, this is expensive. Two teams. Two sets of code. Two sets of bugs. Every feature is specified once and built twice, so every feature can be built slightly differently twice.

Cross-platform frameworks are the answer to that. Write the app once, in one language, and let the framework produce both. That is the whole idea.

What React Native is

React Native comes from Meta. The name is two ideas joined together.

React is a way of building screens that web developers have used for over ten years. You describe what a screen should look like, and the framework decides how to draw it.

Native means what gets drawn is not a web page pretending to be an app. It is the phone’s own real buttons, real lists and real keyboards.

A React Native app is written in JavaScript or TypeScript. Those are the same languages your website almost certainly uses, which is why React Native spread so quickly. A company with web developers already on staff could build a mobile app without hiring two new teams.

What Flutter is

Flutter comes from Google. It is written in a language called Dart, which you will not meet anywhere else.

Flutter does not use the phone’s own buttons. It draws every pixel itself. That sounds like a disadvantage and mostly is not. Drawing everything means a Flutter app looks exactly the same on both phones, which designers like and which keeps a brand consistent.

The trade is that a Flutter app can feel very slightly unlike the phone it is running on. Most users never notice. For your work, Flutter and React Native behave almost identically, and everything below applies to both.

Why a team chose one

Almost always cost and staffing, not technology. A company with web developers picks React Native, because those people can start on Monday. A company starting fresh, or one that wants the same look on both phones, more often picks Flutter. Neither choice was made with analytics in mind, and neither is a problem for you.

Nothing on the Adobe side changes

This is the part worth carrying into a meeting. The schema, the datastream, the tag property, the extensions, consent, identity and Assurance are all identical. None of them knows how the app was built, and none of them cares. They sit on Adobe servers and receive events that look the same whatever produced them.

Three things change, and all three are on the app side.

1. The language your tracking is written in

Not Swift or Kotlin, but JavaScript, or Dart if the app is Flutter. When you read a code sample in Adobe documentation, you need the plugin version rather than the native one. The method names look similar but are not always identical, so a sample copied from the wrong page will not run.

2. How the SDK gets in

A native project adds the SDK through a tool called Swift Package Manager, CocoaPods or Gradle. A React Native project adds it through the JavaScript package manager, npm or Yarn. A Flutter project uses its own tool. It is the same idea every time, and only the command differs. Get the SDK into the app covers the commands.

3. How many times each request is built

This one is good news. One set of code means one implementation. An event fires from one place, so it cannot drift between iPhone and Android.

On a native project, two developers read the same ticket and can build it slightly differently, and then the two numbers never match. On a cross-platform project that cannot happen.

The one real risk

The plugins are wrappers around the native SDK, and a wrapper can fall behind the thing it wraps. When Adobe ships something new, the native SDK gets it first. The React Native and Flutter plugins follow, usually within weeks and sometimes longer.

In practice this rarely causes trouble. Everything you need for an implementation like this one has been supported for years: sending events, identity, consent, lifecycle and Assurance. It becomes a problem only when somebody wants a newer or unusual feature, and it becomes a problem late, after the schema is agreed and the work has started.

So there is one question worth asking at the very beginning, and it costs nothing.

How to recognise one without asking

You can usually tell from the files, and you do not need to read any of them. Recognising the shape is enough.

React NativeFiles ending .js, .jsx or .ts, and a file called package.json.
FlutterFiles ending .dart, and a file called pubspec.yaml.
NativeTwo separate folders, one full of .swift files and one full of .kt files.
✓ What you can now do

You can say what React Native and Flutter are in one sentence each, explain why a team would choose one, and state confidently that nothing on the Adobe side changes. You can ask the one question that matters, about plugin version and feature support. And you know that one set of code removes the most common cause of iPhone and Android numbers disagreeing.
