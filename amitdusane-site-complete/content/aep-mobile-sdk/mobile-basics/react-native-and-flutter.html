Somebody says the app is React Native, and the room nods. Half of them are nodding because they know what that means and half because they do not want to be the person who asks.

This one is worth understanding properly. Cross-platform frameworks are now a large share of the apps you will meet. The honest answer to what changes for you is short, and it is reassuring. Most of what you will read online about this is written for developers deciding which framework to use. You are not deciding. You arrived after the decision was made, probably years after, and you need to know what it means for the work in front of you.

The problem they exist to solve

Apple and Google built two entirely separate worlds. An iPhone app is written in Swift, built in Apple's tool called Xcode, and follows Apple's rules. An Android app is written in Kotlin, built in Google's tool called Android Studio, and follows Google's. The two share almost nothing. A button has to be built twice. So does a list, and a screen transition, and the animation between them. Two people do that work, and neither of them can read the other's.

For a company that wants both, this is expensive in a way that compounds. Two teams. Two codebases. Two sets of bugs. Every feature is specified once and built twice, which means every feature can be built subtly differently twice. And when the business asks for something on a deadline, the deadline is set by whichever team is slower. Cross-platform frameworks are the response to all of that. Write the app once, in one language, and let the framework produce both. That is the entire pitch. When it works, it halves the most expensive part of building an app.

What React Native actually is

React Native comes from Meta, and its name is two ideas stuck together. React is a way of building interfaces that web developers have used for over a decade. You describe what a screen should look like. The framework works out how to draw it, and how to redraw it when something changes. Native is the second half of the promise. What gets drawn is not a web page pretending to be an app. It is the phone's own real buttons, real lists and real keyboards.

So a React Native app is written in JavaScript or TypeScript. Those are the same languages your website almost certainly uses. What it produces is something a user cannot tell apart from a native app. That combination is why it spread so fast. A company with web developers already on staff could build a mobile app without hiring two new teams, and the people it needed were already sitting in the building.

Underneath, there are still two real apps. The framework carries a small piece of native code for each platform, and your JavaScript talks to it across a bridge. That layer is the only place your work changes. Everything else you know still holds.

What Flutter actually is

Flutter comes from Google and takes a different route to the same place. It is written in a language called Dart, which is not a language you will meet anywhere else. Instead of using the phone's own buttons, it draws every pixel itself. That sounds like a disadvantage and mostly is not. Drawing everything means a Flutter app looks precisely the same on both platforms. Designers tend to like that, and it keeps a brand consistent.

It also means the app is never waiting for the framework to support a new native control, because it was never using native controls in the first place. The trade is that a Flutter app can feel very slightly unlike the platform it is sitting on. Most users never consciously notice. For your purposes Flutter and React Native behave almost identically, and everything below applies to both of them equally.

Why a team chose one

Almost always cost and staffing rather than technology. A company with web developers picks React Native because those people can start on Monday. A company starting fresh, or one that cares strongly about a consistent look, more often picks Flutter. Neither choice was made with analytics in mind, and neither is a problem for you.

The three things that change

Here is the part worth carrying into a meeting. Everything on the Adobe side is identical. The schema is the same. So are the datastream, the tag property, the extensions, consent, identity and Assurance. None of them knows how the app was built, and none of them cares. They sit on Adobe servers and receive events that look the same whatever produced them. Nothing in this guide changes on that side, which means the great majority of what you are about to design is unaffected.

Three things change, and all three are on the app side.

The language your tracking is written in. Not Swift or Kotlin but JavaScript, or Dart if the app is Flutter. When you read a code sample in Adobe documentation, you will need the plugin version rather than the native one. The method names are recognisable but not always identical, so a sample copied from the wrong page will not run.

How the SDK gets in. Native projects add dependencies through Swift Package Manager, CocoaPods or Gradle. A React Native project adds them through the JavaScript package manager, npm or Yarn. A Flutter project uses its own tool. It is the same idea in every case, and only the command differs.

How many times each request lands. This one is in your favour. One codebase means one implementation. An event fires from one place, so it cannot drift between iOS and Android. That entire class of discrepancy disappears. The one where a number disagrees between platforms, because two developers read the same ticket differently, simply cannot happen here.

The one real risk, and how to test for it

The plugins are wrappers around the native SDK, and a wrapper can trail what it wraps. When Adobe ships something new, the native SDK gets it first. The React Native and Flutter plugins follow, usually within weeks and occasionally longer. That gap is the only structural risk cross-platform adds to a project like this one.

In practice it almost never bites. The things you need for an implementation like this one have been supported for years and are stable: sending events, identity, consent, lifecycle and Assurance. It bites when somebody wants a newer or more specialised capability, and it bites late, after the schema is agreed and the work is underway. So there is one question worth asking at the very start, and it costs nothing to ask.

How to spot one without asking

You usually can, from things you already have access to. A repository whose files end in .js, .jsx or .ts, and which contains a package.json, is React Native. Files ending in .dart alongside a pubspec.yaml are Flutter. Two separate folders, one full of .swift files and one full of .kt files, is native.

You do not need to read any of those files. Recognising the shape is enough. Being the analytics person who recognises it changes how the rest of the project treats you. It moves you out of the category of people that things have to be explained to.

✓ What you can now do

Say what React Native and Flutter are in a sentence each, explain why a team would choose one, and state confidently that nothing on the Adobe side changes. Ask the one question that matters, about plugin version and feature support. And know that a single codebase quietly removes the most common source of iOS and Android disagreement in mobile reporting.
