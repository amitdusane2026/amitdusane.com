Publishing a tag is an event. Releasing an app is a process with a long tail, and the tail never quite ends.

Before you start

This page will not teach you to build mobile apps. It teaches you enough of the mobile world to understand what a developer is saying, to answer questions in a meeting when no developer is there, and to tell a developer exactly what you need and where it has to change. Words like Xcode, Gradle, native, Flutter and WebView are used here on purpose. You will hear them in every meeting.

A publish is an event. A release is a process.

Publishing a tag property is almost instant. The library is written, the next page load fetches it, and within an hour the old version has effectively stopped existing. Nobody chooses to accept it. You made a change and the world has it.

An app release has almost none of that shape. The build is submitted to a store. It waits for review. It is then made available, which is not the same as delivered. It sits there being offered, and each person decides for themselves whether to take it.

That last step has no web equivalent, and it is where the intuition breaks. On the web, shipping means everyone has it. On mobile, shipping means it is available to be accepted.

The recall notice

A manufacturer issues a recall. The fault is understood, the fix is ready, and the letters go out. What follows is not a switch being thrown. It is a curve.

Some owners go to the garage that week. Most go over the following months, when it suits them. A number never go at all, because they moved, changed the car, or ignored the letter. The manufacturer did everything correctly, and the faulty part is still on the road years later.

An app release behaves like that, with one detail that makes it kinder: most phones have automatic updates switched on, so the majority arrives without anybody deciding anything. That takes the curve from months to days for most of the audience. It does not remove the tail, and the tail is what surprises people.

What sits between submit and installed

Four things, and each takes time that is not yours to compress.

ReviewBoth stores check submissions. Usually quick, not guaranteed to be, and a rejection over something unrelated to your work restarts the clock.
RolloutTeams often release to a percentage of users first, watching for crashes before widening it. Good practice, and it means only some of the audience is on the new version for several days.
AcceptanceAutomatic updates carry most people over a few days, often overnight on wifi. Anybody who switched that off updates when they notice, or never.
EligibilityA new version usually needs a minimum operating system. Anybody on an older phone is never offered it, and stays on an old version permanently.

The versions that never leave

Add those together and you get the fact that matters for measurement. Several versions of your app are always live at once. Not as an edge case. Always.

Last year’s build is still installed on real phones and still being opened, still sending data shaped the way you specified it last year. If you renamed an event six months ago, both names are still arriving. If you fixed a value, the wrong one is still coming in. Your dataset is a blend of every version still in use.

This is why app version belongs on everything, and it arrives automatically on every lifecycle event without anybody asking.

When a number looks wrong, split it by app version first rather than last. A fault on one version and not others is a released bug with a known fix. The same fault across all versions is something else, and knowing which you have is worth ten minutes of anybody’s time.

Where this goes wrong

A tracking fix ships and the metric is checked the same week. It is still wrong, because most of the audience has not updated yet, so the fix looks like it failed. A second fix gets specified for a problem that was already solved. The second release is what finally makes the numbers move, which appears to prove the theory. Splitting by app version on the first check would have shown the new version behaving perfectly all along.

Two things nobody from the web expects

Being wrong is expensive. A wrong value on a website is corrected in an afternoon. The same wrong value in an app is a build, a review, a rollout and a wait, and the bad data keeps arriving throughout. That is the whole argument for specifying carefully rather than iterating quickly.

There is no moment when the change is done. Web work has a clean edge: before the publish and after it. Mobile work has a transition that lasts weeks and never fully completes. So “is the fix live” is not a yes or no question. The honest answer is what proportion of traffic is on a version that has it.

What to move out of the app

All of this points at one rule, and it is the most valuable thing on this page.

Anything that can live in configuration rather than in app code should live in configuration.

The datastream, the tag property, the extension settings and the consent default are all changeable in a browser. They reach installed apps within minutes, with no release. Every decision you push out of the app and into one of those is one you can correct in an afternoon. The alternative is a quarter. What a build actually is sets out where that boundary sits.

The test is one sentence: if getting this wrong would need a release to fix, it is in the wrong place. Apply it while the specification is being written, which is the only time it is free.

Three habits for the release curve
All three are about not being surprised by something predictable.
1
Do Split any suspicious metric by app version before investigating anything else, which is what Release and manage versions sets up.
Why It separates a released bug from a live one in about a minute, and they need completely different responses.
2
Say A fix is measurable in weeks rather than days, and quote adoption rather than a release date.
Why It stops a second fix being specified for a problem the first one already solved.
3
Ask Is this configuration or code, every time you write a requirement.
Why Configuration is correctable this afternoon. Code is correctable next quarter, and the choice is usually still open while you are writing.
✓ What you can now do

You can explain why shipping an app is an offer rather than a delivery, and name the four things between a build and a person running it. You expect several versions to be live at once, and you treat app version as the first split on any suspicious number. You can answer “is the fix live” in terms of adoption rather than dates. And you can push every decision you can out of the app and into configuration, while that choice is still free.
