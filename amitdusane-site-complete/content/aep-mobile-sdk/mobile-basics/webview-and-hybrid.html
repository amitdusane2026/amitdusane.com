A screen in an app can be a web page in disguise. It looks like part of the app, and it is served from a web address like any other page on your website.

Before you start

This page will not teach you to build mobile apps. It teaches you enough of the mobile world to understand what a developer is saying, to answer questions in a meeting when no developer is there, and to tell a developer exactly what you need and where it has to change. Words like Xcode, Gradle, native, Flutter and WebView are used here on purpose. You will hear them in every meeting.

Read this page carefully even if the rest of this section felt familiar. Every other choice about how an app is built changes the language your tracking is written in. This one can change which Adobe product you implement, and it can change it after the schema has been agreed.

What a WebView is

Every phone provides a component that displays a web page inside an app. On iPhone it is called a WKWebView. On Android it is called a WebView. The idea is the same on both.

A WebView is a rectangle on the screen that is, underneath, a browser with none of the browser furniture. No address bar. No tabs. No back button unless somebody drew one.

The page inside is a real web page. It is fetched over the network from a real web address. It runs real JavaScript. It can load anything a browser can load, and that includes your existing web analytics, already built and already collecting.

Why developers use them

Constantly, and usually for good reasons. Terms and conditions are often WebViews. So are help centres, promotions, loyalty programmes and checkout flows.

The content on those screens changes every week. Nobody wants an app store release every time the legal team edits a paragraph, and a release takes days. A web page can be changed this afternoon.

Hybrid apps take that further

If one screen can be a web page, why not most of them? That is what a hybrid app is. The container is a real app you install from a store, and nearly everything inside it is web content running in a WebView. Cordova and Ionic are the tools that build them.

The strength is that a hybrid app is a website your web team already knows how to build, delivered through an app store. The weakness is that users can often feel it. Scrolling is slightly wrong. Screens change slightly too slowly.

Most real apps sit between the two extremes. A native or React Native app with three WebView screens inside it is far more common than a fully hybrid one, and far easier to miss. Nobody thinks to mention three screens, because to the people who built them they are just screens.

Why this matters more than the rest

The Mobile SDK lives in the app and measures the app. A WebView is a browser, and the Mobile SDK cannot see inside it.

So somebody opens a WebView screen, reads it for four minutes and buys something. As far as the Mobile SDK is concerned, that person did nothing at all.

Meanwhile the page inside that WebView can carry the Web SDK, exactly as your website does, and can measure itself perfectly well. That gives you three possible arrangements.

Mobile onlyRight when WebViews are incidental: a terms page, a help centre, anything nobody needs measured. Those screens are invisible in reporting, and that is an acceptable gap.
BothRight when WebView screens carry real behaviour, such as checkout. The app measures itself, the pages measure themselves, and the two are joined by a shared identifier. This needs deliberate design.
Web mostlyRight for a genuinely hybrid app, where nearly everything is web content. The Mobile SDK still earns its place for lifecycle and installs, which no web page can see.

The trap in the middle option

The second arrangement is the common one, and it is the one that causes problems.

Two implementations are measuring one person. Unless they are joined deliberately, that person becomes two people.

The app knows the person by an ECID, which is the visitor ID Adobe assigns, stored in the app’s own storage. The page inside the WebView is a browser, so it gets its own ECID, stored in browser storage. Same human, same phone, same session, two identities.

The result is that the checkout looks like it was done by a stranger who arrived from nowhere.

Neither side is broken. Each is doing its job correctly. The damage is done by a join that nobody specified, which is why this has to be settled before the schema rather than after the numbers look wrong.

There is a second problem in the same place. The two can measure the same thing twice. The app fires an event when the WebView opens, and the page fires its own event when it loads. One action has now produced two records, and reports quietly run high. Nobody sees an error, because nothing has gone wrong in a way any system can detect.

How the two sides are joined

You will be asked whether this can be fixed. It can, and the mechanism is worth knowing in outline.

The app reads its own ECID from the SDK and passes it into the WebView. There are two ordinary ways to do that. The ECID can be added to the web address the WebView loads, as a parameter the page reads on arrival. Or the app can put it directly into the page once the page has loaded.

The page then tells the Web SDK to use that identity instead of creating its own. Both sides are now talking about the same person, and the app journey and the page journey join into one. Set up identity carries the exact call.

Two details decide whether it works.

Every oneThe identity has to be passed into every WebView, not just the first, because each one is a fresh browser.
EarlyIt has to be passed before the page sends anything. If the first event carries the wrong identity, nothing later can repair it.
Where this goes wrong

Nobody mentions the WebView screens, because nobody thinks of them as screens. The implementation is built, checked and approved. Then somebody asks why checkout conversion looks impossible. Two implementations were measuring one journey and disagreeing about who the customer was, and the fix needed a plan that was never made.

How to find them

Asking works, but ask precisely. “Are there any web views?” invites a no from somebody who is thinking about the main navigation and has forgotten the loyalty section. They are not hiding anything. They answered the question you asked.

Ask which screens are web content and you get a list instead.

There is also a test you can run yourself, on your own phone, in a minute. Open the app and go to a screen you suspect. Turn on airplane mode, then pull down to refresh, or leave the screen and come back.

A native screen usually still appears, because its layout was built into the app. A WebView screen tends to go blank or show a connection error, because it was fetching a page and the page never arrived.

The test is not perfect, and it is very useful. It also shows the app team that the analytics person is paying attention to how the thing is really built, which changes what they tell you next time.

✓ What you can now do

You know that a screen can be a web page, and you can ask which screens are web content rather than whether any are. You know that a WebView carrying real behaviour needs the Web SDK inside it and a shared identity with the app around it. And you know to settle this before the schema is designed, because it decides whether you are implementing one thing or two.
