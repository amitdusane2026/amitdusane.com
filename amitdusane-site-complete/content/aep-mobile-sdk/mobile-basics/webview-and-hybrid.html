A screen in an app can be a web page wearing a costume. It looks native, it behaves almost native, and it is served from a URL like anything else on your website.

This is the only topic in this section that can change which guide you should be reading, so it is worth reading carefully even if the rest feels familiar. Every other decision about how an app is built changes the language your tracking is written in. This one can change the product you implement.

What a WebView is

Every phone provides a component that displays a web page inside an app. On iOS it is called a WKWebView and on Android a WebView, and the idea is the same on both: a rectangle on the screen that is, underneath, a browser without any of the browser furniture. No address bar, no tabs, no back button unless somebody drew one.

The page inside it is a real web page. It is fetched over the network from a real URL, it runs real JavaScript, and it can load anything a browser can load, including your existing web analytics.

Developers reach for this constantly, and usually for good reasons. Terms and conditions, help centres, promotional campaigns, loyalty programmes and checkout flows are frequently WebViews, because the content changes weekly and nobody wants a store release every time the legal team edits a paragraph. Remember what an app release costs and the appeal is obvious.

Hybrid apps take that to its conclusion

If one screen can be a web page, why not most of them? That is what a hybrid app is. The container is a real app you install from a store, and nearly everything inside it is web content running in a WebView. Apache Cordova and Ionic are the frameworks that do this, and they were popular enough that you will meet their output for years to come.

The strength is that a hybrid app is a website your web team already knows how to build, delivered through an app store. The weakness is that users can often feel it. Scrolling is slightly wrong, transitions are slightly slow, and the app is slightly less responsive than its native neighbours.

Most real apps sit between the extremes. A native or React Native app with three WebView screens in it is far more common than a fully hybrid one, and it is also far easier to miss, because nobody thinks to mention three screens.

Why this matters more than the rest

The Mobile SDK lives in the app and measures the app. A WebView is a browser, and the Mobile SDK cannot see inside it. As far as the SDK is concerned, a person who opens a WebView screen, reads it for four minutes and buys something has done nothing at all.

Meanwhile the page inside that WebView can carry the Web SDK, exactly as your website does, and measure itself perfectly well.

So there are three possible arrangements, and picking the wrong one is expensive in a way the other decisions in this section are not.

The three arrangements
Mobile SDK onlyRight when WebViews are incidental: a terms page, a help centre, anything nobody needs measured. The screens are invisible to reporting and that is an acceptable gap.
Both, carefullyRight when WebView screens carry real behaviour, such as checkout. The app measures itself, the pages measure themselves, and the two are joined by a shared identifier. This needs deliberate design.
Web SDK mostlyRight for a genuinely hybrid app, where nearly everything is web content. The Mobile SDK still earns its place for lifecycle and installs, which no web page can see.

The trap in the middle option

The second arrangement is the common one and the one that goes wrong. Two implementations measuring one person, and unless they are joined deliberately, that person is two people.

The app knows them by an ECID stored in app storage. The page inside the WebView is a browser and gets its own ECID, stored in browser storage. Same human, same phone, same session, two identities, and a checkout that appears to have been done by a stranger who arrived from nowhere.

Worse, the two can measure the same thing twice. If the app fires an event when the WebView opens and the page fires its own on load, one action produces two records, and reports quietly run high.

None of this is unsolvable. Identity is passed from the app into the WebView so that both sides agree who they are talking to, and the two implementations are specified together so neither measures what the other measures. It is real design work, done once, at the start. It is very unpleasant to retrofit.

How the two sides are joined

The mechanism is worth knowing in outline, because you will be asked whether it is possible and the answer is yes.

The app reads its own ECID from the SDK, and passes it into the WebView. There are two ordinary ways to do that. It can be added to the URL the WebView loads, as a parameter the page reads on arrival. Or the app can inject it directly into the page once loaded, which developers describe as evaluating JavaScript in the WebView.

The page then tells the Web SDK to use that identity rather than minting its own. Both sides are now talking about the same person, and behaviour in the app and behaviour in the page join into one journey.

Two details decide whether it works. The identity has to be passed on every WebView, not just the first, because each one is a fresh browser context. And it has to be passed before the page sends anything, or the first event carries the wrong identity and nothing later can repair it.

This is a conversation to have with whoever owns the web implementation as well as the app team, and it is short if you have it early.

Where this goes wrong

Nobody mentions the WebView screens because nobody thinks of them as screens. The implementation is built, validated and signed off, and then somebody asks why checkout conversion looks impossible. Two implementations were measuring one journey and disagreeing about who the customer was, and the answer needed a plan that was never made.

How to find them

Asking works, but ask precisely. "Are there any web views" invites a no from somebody who is thinking about the main navigation and has forgotten the loyalty section. Ask which screens are web content and you get a list.

There is also a test you can run yourself, on your own phone, in a minute. Open the app and go to a screen you suspect. Turn on airplane mode and pull down to refresh, or navigate away and back. A native screen usually still renders, because its layout was compiled into the app. A WebView screen tends to go blank or show a connection error, because it was fetching a page.

It is not infallible and it is remarkably useful. It also demonstrates something to the app team, which is that the analytics person is paying attention to how the thing is actually built.

✓ What you can now do

Recognise that a screen can be a web page, ask which screens are web content rather than whether any are, and know that a WebView carrying real behaviour needs the Web SDK inside it and a shared identity with the app around it. Settle this before the schema is designed, because it decides whether you are implementing one thing or two.
