A screen in an app can be a web page wearing a costume. It looks native, it behaves almost native, and it is served from a URL like anything else on your website.

This is the only topic in this section that can change which guide you should be reading. It is worth reading carefully even if the rest of this felt familiar. Every other decision about how an app is built changes the language your tracking is written in. This one can change the product you implement, and it can change it after the schema has been agreed.

What a WebView is

Every phone provides a component that displays a web page inside an app. On iOS it is called a WKWebView. On Android it is called a WebView. The idea is the same on both. It is a rectangle on the screen that is, underneath, a browser without any of the browser furniture. No address bar. No tabs. No back button unless somebody drew one.

The page inside it is a real web page. It is fetched over the network from a real URL. It runs real JavaScript. It can load anything a browser can load, and that includes your existing web analytics, already deployed, already collecting.

Developers reach for this constantly, and usually for good reasons. Terms and conditions are frequently WebViews. So are help centres, promotional campaigns, loyalty programmes and checkout flows. The content on those screens changes weekly. Nobody wants a store release every time the legal team edits a paragraph. Remember what an app release costs and the appeal becomes obvious.

Hybrid apps take that to its conclusion

If one screen can be a web page, why not most of them? That is what a hybrid app is. The container is a real app you install from a store, and nearly everything inside it is web content running in a WebView. Apache Cordova and Ionic are the frameworks that do this. They were popular enough that you will meet their output for years to come.

The strength is that a hybrid app is a website your web team already knows how to build, delivered through an app store. The weakness is that users can often feel it. Scrolling is slightly wrong. Transitions are slightly slow. The app is slightly less responsive than its native neighbours.

Most real apps sit between the two extremes. A native or React Native app with three WebView screens in it is far more common than a fully hybrid one. It is also far easier to miss. Nobody thinks to mention three screens, because to the people who built them they are just screens.

Why this matters more than the rest

The Mobile SDK lives in the app and measures the app. A WebView is a browser, and the Mobile SDK cannot see inside it. Somebody opens a WebView screen, reads it for four minutes and buys something. As far as the SDK is concerned, that person has done nothing at all. Meanwhile the page inside that WebView can carry the Web SDK, exactly as your website does, and can measure itself perfectly well.

So there are three possible arrangements. Picking the wrong one is expensive in a way that the other decisions in this section are not, because the cost arrives late and lands on somebody else's deadline.

The three arrangements
Mobile SDK onlyRight when WebViews are incidental: a terms page, a help centre, anything nobody needs measured. The screens are invisible to reporting and that is an acceptable gap.
Both, carefullyRight when WebView screens carry real behaviour, such as checkout. The app measures itself, the pages measure themselves, and the two are joined by a shared identifier. This needs deliberate design.
Web SDK mostlyRight for a genuinely hybrid app, where nearly everything is web content. The Mobile SDK still earns its place for lifecycle and installs, which no web page can see.

The trap in the middle option

The second arrangement is the common one, and it is the one that goes wrong. Two implementations are measuring one person. Unless they are joined deliberately, that person is two people. The app knows them by an ECID stored in app storage. The page inside the WebView is a browser and gets its own ECID, stored in browser storage. Same human, same phone, same session, two identities. The checkout appears to have been done by a stranger who arrived from nowhere.

Worse, the two can measure the same thing twice. The app fires an event when the WebView opens. The page fires its own event on load. One action has now produced two records, and reports quietly run high. Nobody sees an error, because nothing has gone wrong in any way a system can detect.

None of this is unsolvable. Identity is passed from the app into the WebView, so that both sides agree who they are talking to. The two implementations are specified together, so neither measures what the other measures. It is real design work, done once, at the start. It is very unpleasant to retrofit, and retrofitting is when most teams meet it.

How the two sides are joined

The mechanism is worth knowing in outline, because you will be asked whether it is possible and the answer is yes. The app reads its own ECID from the SDK and passes it into the WebView. There are two ordinary ways to do that. It can be added to the URL the WebView loads, as a parameter the page reads on arrival. Or the app can inject it directly into the page once loaded, which developers describe as evaluating JavaScript in the WebView.

The page then tells the Web SDK to use that identity rather than minting its own. Both sides are now talking about the same person. Behaviour in the app and behaviour in the page join into one journey, and the checkout stops looking like a stranger.

Two details decide whether it works. The identity has to be passed on every WebView, not just the first, because each one is a fresh browser context. And it has to be passed before the page sends anything. If the first event carries the wrong identity, nothing later can repair it. This is a conversation to have with whoever owns the web implementation as well as the app team, and it is a short conversation if you have it early.

Where this goes wrong

Nobody mentions the WebView screens because nobody thinks of them as screens. The implementation is built, validated and signed off, and then somebody asks why checkout conversion looks impossible. Two implementations were measuring one journey and disagreeing about who the customer was, and the answer needed a plan that was never made.

How to find them

Asking works, but ask precisely. "Are there any web views" invites a no from somebody who is thinking about the main navigation and has forgotten the loyalty section. They are not hiding anything. They answered the question you asked. Ask which screens are web content and you get a list instead.

There is also a test you can run yourself, on your own phone, in a minute. Open the app and go to a screen you suspect. Turn on airplane mode, then pull down to refresh or navigate away and back. A native screen usually still renders, because its layout was compiled into the app. A WebView screen tends to go blank or show a connection error, because it was fetching a page and the page never arrived.

The test is not infallible, and it is remarkably useful. It also demonstrates something to the app team. The analytics person is paying attention to how the thing is actually built, which changes what they tell you next time without anybody discussing it.

✓ What you can now do

Recognise that a screen can be a web page, and ask which screens are web content rather than whether any are. Know that a WebView carrying real behaviour needs the Web SDK inside it, and a shared identity with the app around it. Settle this before the schema is designed, because it decides whether you are implementing one thing or two.
