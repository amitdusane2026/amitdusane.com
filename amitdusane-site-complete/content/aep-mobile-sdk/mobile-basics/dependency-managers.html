Nobody copies the Adobe SDK into an app. They write down its name and a version, and a tool fetches it while the app is being built.

A ticket goes to the mobile team saying add the Adobe SDK. It sounds like one action. On the web it would be one action, roughly equivalent to pasting a script tag into a page template. That impression survives right up until something goes wrong. Then a developer mentions that the versions are not aligned, or that the build failed while resolving dependencies. The conversation moves somewhere you cannot follow it. The vocabulary is unfamiliar and the concepts underneath it are not.

You are never going to type any of this. You should still understand the shape of it. Two of the things that commonly go wrong in a mobile implementation go wrong here. Both are visible in a short block of text. A developer can paste it into a message in ten seconds. Reading that block is a skill worth ten minutes, and it does not require knowing the language it is written in.

A list, not a parcel

The Adobe SDK does not get copied into the project. What goes into the project is a list, and that list names each library the app depends on. When somebody builds the app, a tool reads that list. It downloads each library from a public repository and links the results into the build. The libraries are not stored alongside the company's own code. They arrive fresh every time anybody builds.

That tool is a dependency manager, and every serious project has one. The arrangement is closer to a shopping list than to a delivery. The list is the part that lives in the code, gets reviewed, and can be argued about in a pull request. The goods themselves come from somewhere else, at the last moment, and nobody looks at them on the way in. This is completely standard practice and it is not a weakness. It is how essentially all modern software is assembled.

One consequence matters to you immediately. Two developers can build from identical code and finish with different libraries inside their apps. That happens whenever the list allows any latitude about which version to fetch. The code was the same and the list was the same. What the list resolved to was not, and nothing in the process announces that it has happened.

Three tools doing one job

Three names come up, and the differences between them are much smaller than the job they share. On iOS, Swift Package Manager is Apple's own and is built directly into Xcode. CocoaPods is older, was the standard for years, and is still in a great many production apps that are not worth migrating. On Android there is Gradle, which handles dependencies and is also the build system itself rather than a separate tool bolted onto one.

All three read a list of libraries, fetch them, and resolve versions so the set fits together. Which one a project uses was decided years ago, usually by whoever started it. That choice is not worth relitigating now. The choice changes the file a developer opens and the command they run. It changes nothing you are going to ask for, and nothing about how the Adobe SDK behaves once it is in there.

The SDK is not one library

Here is the fact that makes versions matter at all. The Adobe Mobile SDK is not a single library. It is a set of them, usually six or seven in a working implementation. They are built, tested and released together as a matched set.

Core is one of them. Identity is another. So are Lifecycle, Signal, the Edge extensions and the Assurance extension. Each is a separate library with its own version number, listed separately and fetched separately by the dependency manager. Each one expects the others to come from the same release, because that is the only combination anybody tested. They are components of one product that happen to be delivered as several parcels.

Mix versions from different releases and one of two things happens. Either the build fails outright, which is the good outcome, because somebody has to deal with it before anything can ship. Or the app builds successfully and behaves strangely afterwards. That second outcome reaches you weeks later, as a data problem with no obvious cause. By then nobody connects it to a dependency file. That file was edited during a different piece of work entirely.

The bill of materials, and why it is the answer

Adobe solves this on Android with a bill of materials, published as an artefact called sdk-bom. It is a single line declaring a known-good combination of every library in the set. Each Adobe library listed after it inherits its version from that combination. That is why the individual libraries carry no version numbers of their own.

implementation platform('com.adobe.marketing.mobile:sdk-bom:3.+')
implementation 'com.adobe.marketing.mobile:core'
implementation 'com.adobe.marketing.mobile:identity'
implementation 'com.adobe.marketing.mobile:signal'
implementation 'com.adobe.marketing.mobile:lifecycle'

The arrangement is visible in that block even without knowing Gradle. The first line pins the set. The four lines after it name members of the set and state no version at all. The first line already decided for them. Adding a fifth extension later means one more line with no version on it. It cannot drift out of step with the others, because there is no separate number on it to drift.

The equivalent discipline on iOS is one consistent version range across all the Adobe packages. The alternative is each package pinned by hand, to whatever happened to be current on the day somebody added it. The mechanism differs from Android and the principle does not. One decision about versions, made once, in one place. The alternative is seven decisions, made on seven different afternoons, by people who were each solving something else.

Adobe's own example uses 3.+, which means the latest release of major version three. That is a reasonable default and it is not the strictest option available. The + is a moving target, so two builds a month apart can legitimately resolve to different versions. A team that needs builds to be reproducible later will pin an exact bill of materials version instead. They then raise it deliberately, when they choose to. That is the arrangement worth asking for on anything subject to audit.

Reading a dependency block without knowing the language

Real value comes out of this without learning Gradle or Swift. Ask a developer to paste the Adobe lines from the dependency file. It takes them about ten seconds and requires no preparation. Then read the shape of what comes back rather than the syntax of it, looking for three things.

A bill of materials line, or on iOS one version range covering everything, means somebody has thought about this. The set will stay coherent on its own. Seven Adobe lines each carrying its own version number means nobody has thought about it. The set will drift the first time one of them is updated alone. Versions that visibly disagree, a five on one line and a three on another, are worth asking about. The alternative is a week spent debugging behaviour with a one-line cause.

That is the whole of the skill, and it is smaller than it sounds. You are not auditing the build or second-guessing an engineer. You are checking that one decision was made deliberately rather than by accident. It is very cheap to ask at the start of an implementation and expensive to ask after a release. Almost everything in this section follows that pattern.

Where this goes wrong

An extension is added months after the original implementation, pinned by hand to whatever version was current that week. Everything builds and the app ships. The mismatch surfaces later as behaviour nobody can reproduce: events arriving intermittently, or an extension that registers on one platform and not the other. The dependency block had the answer in it the whole time, and nobody outside the mobile team had ever looked at it.

What to ask for

Two requests cover everything on this page. Neither asks a developer to justify themselves, which is part of why both land well. They are questions about arrangement rather than about competence. The answer to the second one usually contains the answer to the first.

Two things, once, early
Ask at the start of the implementation, not when something is already wrong.
1
Ask On Android, is the bill of materials in use? On iOS, is there one version range across the Adobe packages?
Why It is the difference between a set that stays coherent by design and one that stays coherent by luck.
2
Ask Paste the Adobe dependency lines as they currently stand.
Why Ten seconds of a developer's time, and it answers the first question and several you have not thought of yet.
✓ What you can now do

Say what a dependency manager does, and why an app fetches the SDK rather than containing it. Name the three tools, and know that the choice between them changes nothing you will ask for. Explain why the Adobe libraries are a matched set, and why mixing versions produces either an honest build failure or a dishonest data problem. And read a dependency block well enough to tell a deliberate arrangement from an accidental one.
