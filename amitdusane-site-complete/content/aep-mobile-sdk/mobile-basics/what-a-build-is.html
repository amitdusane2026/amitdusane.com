A web page is delivered as the text somebody wrote. An app is delivered as a sealed file made from that text, and the text is nowhere inside it.

Before you start

This page will not teach you to build mobile apps. It teaches you enough of the mobile world to understand what a developer is saying, to answer questions in a meeting when no developer is there, and to tell a developer exactly what you need and where it has to change. Words like Xcode, Gradle, native, Flutter and WebView are used here on purpose. You will hear them in every meeting.

What a compiler does

A developer writes Swift or Kotlin. Those languages are meant for people to read, and a phone cannot run either of them.

So a program called a compiler translates that text into instructions the phone understands. It packages the result with the images, fonts, sounds and settings the app needs. What comes out is a single file. That file is the app, and it is what reaches a phone.

The translation only runs one way. You cannot take the finished file and get the Swift back. There is no view-source for an app, no way to open it and read the tracking call, and no way to edit one value inside it.

Why a wrong value takes two weeks to fix

On the web you would fix it within the hour, and you might fix it yourself. Open the tag property, correct the text, publish. The next person to load the page sees the new value.

Ask for the same correction in an app and you get a date, usually two weeks away, from somebody being completely straight with you.

Think of a printed newspaper. A website is corrected by editing the page. A newspaper is corrected by printing tomorrow’s edition, because forty thousand copies are already on trains and doorsteps. The correction itself is easy. The problem is that the thing carrying the mistake has already left the building.

Everything else follows from that. Corrections are collected and printed together, because a second run costs the same whether it fixes one word or the whole front page. The edition is checked carefully before it goes, because checking afterwards changes nothing. And when somebody asks what the paper said, the honest question back is which edition they read.

Six characters and six thousand lines cost the same

Changing one word means compiling the whole app again. The new file is then tested, signed, submitted, reviewed by the store, and released. Nothing in that sequence cares how big the change was.

Once that is clear, behaviour that looks obstructive is actually sensible. Changes are collected together, because the expensive part is the release, not the edit. Small requests wait for a build that is going anyway. A ticket that arrives the day after a submission waits for the next one, which may be two weeks.

So the shape of your request matters more than its size. Six separate tracking tickets across a quarter cost six releases. The same six requirements in one specification cost one. Ask for everything you need at once, including the parts you are not sure about, because a value that ships unused is cheaper than a change that has to be added later.

✓ The exception, and it is most of your work

Anything the mobile tag property controls is fetched by the SDK while the app runs, rather than compiled into it. Changing a datastream, adjusting an extension’s settings, or altering the tag property reaches installed apps within minutes and needs no release. The edge is precise and worth memorising: configuration travels freely; anything that needs a new line of code in the app does not.

Knowing which road a request is on is most of what this page buys you. Asking for a code change and a configuration change in the same breath is what produces false urgency and false patience, usually in the same meeting.

What you lose when code becomes a sealed file

Web work depends on tools that let you see inside the running thing. None of them exist here, and each absence is worth naming.

No consoleNowhere to paste a check and see the answer.
No network tabNo list of the requests the app made.
No inspectorThe screen was not built from markup, so there is nothing to inspect.
No proofNo way to confirm from outside that a tracking call exists at all.

On the web you answer all four of those yourself, in about ninety seconds, without asking anybody.

This is why Assurance exists and why it is not optional. A compiled app is closed from the outside, so the only way to see inside a running one is a tool the app itself invites in. Assurance is that invitation, it is the network tab you no longer have, and it has to be built into the app before it can show you anything.

The question you have to change

On the web, asking whether something is in the code makes sense, because the code and the live site are the same thing. In an app they are two different objects with two different histories. The code can be perfectly correct while the app on your phone knows nothing about it.

So stop asking “is the tracking in the code”, which a developer will honestly answer yes to. Ask which build is it in.

Those are different questions. The first is about a file on somebody’s machine. The second is about the thing you are holding, and it is the only one of the two you can test. Most confused validation sessions are two people answering different questions and agreeing with each other.

Version and build number are not the same

The version is the public one, something like 4.2.1, and it is what a customer sees in the store.

The build number counts every attempt underneath that version. One public version routinely covers twenty or thirty builds, because each submission, each internal test and each fix produces another.

So two people can both be running version 4.2.1 and be running different software. A version number alone never settles a validation question. Ask for both and write them next to whatever you saw. It costs one extra line in a ticket, and it saves the day two people spend hunting a fault that is really just one build apart.

What to ask, and when

None of this needs you to read code. It needs you to ask about builds rather than about code, early enough that the answer can still change something.

Three habits that pay for themselves
None of these takes a developer more than a minute to answer.
1
Ask Which build is this, by version and build number, and is it the one in the store?
Why It separates a fault in the code from a fault in the app you are testing. Different people fix those.
2
Ask When is the next release going out, and what is already in it?
Why It tells you which train your request can still catch, and catching one costs nothing extra.
3
Ask Is this request configuration or code?
Why Configuration reaches phones this afternoon. Code waits for a build.
✓ What you can now do

You can explain why an app cannot be corrected the way a page can, without apologising for it. You can ask which build a number came from rather than whether the code is right. You know that collecting requests together is sensible rather than obstructive, so you can shape your specifications for it. And you can tell a change that ships this afternoon from one that waits two weeks, before you promise either to anybody.
