There are four ways to build a mobile app. All four look the same on a phone. Underneath they are completely different, and the difference decides who you work with and what you can ask them for.

Before you start

This page will not teach you to build mobile apps. It teaches you enough of the mobile world to understand what a developer is saying, to answer questions in a meeting when no developer is there, and to tell a developer exactly what you need and where it has to change. Words like Xcode, Gradle, native, Flutter and WebView are used here on purpose. You will hear them in every meeting.

The four kinds

Somebody chose how this app would be built, often years ago, for reasons that had nothing to do with analytics. Nobody wrote the choice down where you can see it. Nobody will think to tell you either. So ask.

NativeWritten twice. One version for iPhone, one for Android. Two teams, two languages.
Cross‑platformWritten once, then turned into both apps by a framework. React Native and Flutter.
HybridWeb pages inside a thin app. Cordova and Ionic.
Game engineBuilt in a game tool, almost always Unity.

Why there are four

There are two phones. Apple’s iPhone runs iOS. Most other phones run Android. The two share almost nothing underneath: different programming languages, different tools, different rules about what an app may do.

A company that wants to reach everybody has to build for both. Each of the four kinds is a different answer to that one problem. Each answer trades cost against quality.

Native: written twice

A native app is built twice. One team writes the iPhone version in a language called Swift. A second team writes the Android version in a language called Kotlin. The two are separate programs that happen to look the same and do the same things.

Native gives you everything the phone can do, on the day the phone can do it. Every Adobe SDK feature works immediately, because Adobe builds the SDK for native first.

The cost is that every request you make is built twice. You ask for one tracking event. Two developers read your one ticket, in two languages, on two schedules. They can build it slightly differently. Then the iPhone number and the Android number never match, and nothing tells you why.

Cross-platform: written once

A cross-platform app is written once, in one language. A framework then turns that single set of code into both apps. The two frameworks you will meet are React Native and Flutter.

This is much cheaper, and for most apps the result is good enough that users never notice. The trade is speed of support. When Apple or Google adds something new, the framework has to catch up first, and that takes months rather than days.

For you this is good news. Adobe ships a plugin for both frameworks. Both plugins use the same native SDK underneath, so everything on the Adobe side behaves identically. One set of code also means your request is built once, so the iPhone and Android numbers cannot drift apart.

Hybrid: web pages inside an app

A hybrid app is a thin app shell with web pages inside it. You install it from the app store like any other app, but much of what you see is a website. The component that displays a web page inside an app is called a WebView. Cordova and Ionic are the tools that build apps this way.

Hybrid is the cheapest of the four and the fastest to ship. Users can often tell.

This kind matters more than the others, because it can change which Adobe product you implement. A WebView is a browser, and the Mobile SDK cannot see inside a browser. If a screen is a web page, that page can carry the Web SDK instead, exactly as your website does.

Ask about this on day one

If anybody says the app is Cordova, Ionic, or mostly web views, find out which screens are web pages before you agree to any approach. That one answer can change the whole shape of the project, and it is far cheaper to ask now than to discover it during testing. WebView and hybrid apps covers it in full.

Game engines

The fourth kind is built in a game engine, almost always one called Unity. Games use it. So do some things that are not games: 3D product views, training simulators, some marketing apps. The language is usually C#.

Adobe’s support for game engines is thinner than for the other three. If you get one, expect more custom work and fewer people who have done it before you.

What changes for you

Less than you might fear. Everything on the Adobe side is identical in all four cases. The schema, the datastream, the tag property, the extensions, consent, identity and Assurance do not know how the app was built, and do not care. They sit on Adobe servers and receive events that look the same whatever produced them.

Three things change, and all three are on the app side.

LanguageSwift and Kotlin for native. JavaScript for React Native. Dart for Flutter. C# for Unity.
Adding itEach kind adds the SDK its own way. Same idea every time, different command.
RepeatsNative builds every request twice. The other three build it once.

How to find out which one you have

You do not need to read any code. Ask, and the answer arrives in one sentence. But ask precisely. “It is an app” is not an answer, and people offer it in good faith, because to them the question sounded already settled.

Three questions, in the first conversation
Any developer can answer all three in under a minute.
1
Ask Is there one set of code or two? Two means native. One means cross-platform, hybrid or a game engine.
2
Ask What is it written in? Swift or Kotlin means native. JavaScript means React Native or hybrid. Dart means Flutter. C# usually means Unity.
3
Ask How much of the screen is a web view? If the answer is anything other than none, find out exactly which screens before going further.
✓ What you can now do

You can sit in a kick-off meeting and ask three short questions. The answers tell you whether this is one set of code or two, which language your tracking will be written in, and whether the WebView question has to be settled before anything else starts.
