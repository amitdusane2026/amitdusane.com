You are not learning to program. You are learning to look at four lines somebody pasted into a ticket and say something useful about them.

A developer pastes a snippet into a thread and asks whether it looks right. Everybody waits. The honest answer is that you cannot tell. So the thread becomes a meeting. The meeting then establishes something that was visible in the snippet the whole time. Nobody in that thread lacked skill. The person who could see it was not looking, and the people looking could not see it.

The gap here is much smaller than it looks. You do not need to write a line of Swift or Kotlin, ever, and you should not offer to. What you need is to recognise five shapes, and to know which single question the code can answer for you. That is an afternoon of attention rather than a course. None of it makes you a developer, and none of it is meant to.

What you are actually trying to find out

Start with the question, because it keeps the rest in proportion. You are almost never asking whether the code is good. That is not your call and you have no basis for it. Whether it is idiomatic, efficient or well structured is a developer's judgment. Offering one costs you standing rather than earning it.

You are asking three much narrower things. Does the tracking call exist at all. Does it carry the values your specification asked for. And is it in the place your specification asked for. That is the whole list, and all three are answerable by reading rather than by understanding. That distinction is the whole trick. You are matching text against a specification, not following logic.

Everything on this page serves those three. Anything beyond them belongs to the developer. The moment you drift into opinions about the code itself, you stop being useful and start being expensive. The line is easy to cross, because reading a little makes the next step feel available.

Five shapes worth recognising

Programming languages differ far less than they appear to, and the differences are mostly punctuation. Five shapes carry almost everything you will need. A function call is a name followed by brackets: sendEvent(...). Something is being done, and the name usually says what. A string is text in quotes, and this is where your values live. If your specification said the event should be called purchase, the word purchase should be visible in quotes somewhere.

A variable is a name with no quotes around it, standing in for a value decided elsewhere. This is the one that matters most, and the next section is about why. A condition starts with if and means the code below only runs sometimes. A comment starts with // and is a note to humans that the machine ignores entirely.

That is enough to read a tracking call. Not enough to review one, and not enough to suggest a change, which are different activities you are not being asked to do. Knowing where the skill stops is as useful as the skill itself.

The same call, in three languages

Here is a tracking call in Swift, which is iOS. Two things are happening: a dictionary of values is assembled, then it is sent. Read past the punctuation and the shape is plain enough.

var xdmData : [String: Any] = ["eventType" : "SampleXDMEvent",
                              "sample": "data"]

let experienceEvent = ExperienceEvent(xdm: xdmData)
Edge.sendEvent(experienceEvent: experienceEvent)

Read it as a sentence and it is not mysterious. The first part builds a labelled list of values, and the words in quotes are yours: eventType is a field name from the schema. The value beside it is what will arrive in the dataset. The last line sends it. The name Edge tells you which extension is doing the sending, and sendEvent tells you what it is doing.

Now the same thing on Android, in Kotlin. The punctuation changes and nothing else does. Notice that the words in quotes are identical to the Swift version. Those come from your schema rather than from the language.

val xdmData = mutableMapOf<String, Any>()
xdmData["eventType"] = "SampleXDMEvent"
xdmData["sample"] = "data"

val experienceEvent = ExperienceEvent.Builder()
  .setXdmSchema(xdmData)
  .build()

Edge.sendEvent(experienceEvent)

Same three parts, in the same order. Values are collected under field names, an event is assembled from them, and the event is sent. If you can find the field names and the values in one of these, you can find them in the other. That is genuinely most of the skill.

The variable is where the real faults hide

Here is the single most useful thing on this page. Look at what is not in quotes. A value in quotes is fixed and you can read it directly. A value that is a bare name is decided somewhere else, at the moment the code runs. You cannot see it from the snippet at all. Both look equally correct in a ticket, and only one of them can be verified by looking.

xdmData["eventType"] = "commerce.purchases"   // fixed, and readable
xdmData["currencyCode"] = cart.currency       // decided elsewhere, invisible here

The second line might be perfect. It might also be empty on the screens where the cart has not loaded, or lowercase where your schema expects uppercase, or null for guest checkout. Nothing in the snippet tells you, and no amount of staring will. That is not a fault in the code, it is a limit on what reading can establish.

So when you see a bare name where a value should be, you have found the one thing worth asking about. What is that at run time, and what is it when things go wrong? Then you confirm the answer in Assurance, on a real device, because that is the tool that shows the value rather than the intention.

The skill that beats reading: searching

Reading a snippet somebody chose to show you is the weak version. The strong version is finding out whether something exists at all, and that is searching rather than reading. A snippet answers whether one call is right. A search answers whether the call exists anywhere, which is a different and usually more urgent question.

You do not need repository access to benefit from this, though it helps if you have it. What you need is to ask the right search, and to ask a developer to run it if you cannot. Searching for sendEvent finds every place the app sends anything. Searching for a field name from your schema finds every place that field is populated. More usefully, it reveals whether that is one place or nine.

That second answer is the valuable one and it is invisible from any single snippet. A field set in one place is a field you can reason about. The same field set in nine places, by four people, over two years, is something else. It is the explanation for a value that is right most of the time. Consistency is not something you can read out of one snippet, and it is very often the answer.

What not to do with this

One boundary, stated plainly, because crossing it costs more than the skill is worth. Do not propose code changes. Reading four lines does not qualify anybody to edit them. An analytics person who arrives with a suggested patch has moved from their side of the line to somebody else's. Where your job ends sets out that line in full. The developer now has to review your code and manage the conversation, which is slower than if you had simply described the problem.

Describe what you observed and what you expected. "The event fires on the confirmation screen but currencyCode arrives empty for guest checkout" is worth a great deal. It takes no position on how it should be fixed. That sentence is what reading code is for. Everything else on this page exists so that you can write that one sentence with confidence.

What to do with a snippet in a ticket
Four passes, in this order, and none of them needs the developer present.
1
Find The field names and values in quotes, and check them against your specification.
Why Misspelled field names are the most common fault and the easiest to see.
2
Find The values that are not in quotes.
Why Those are the ones no snippet can verify, so they are the ones worth a question.
3
Ask For a search, not a snippet: how many places set this field?
Why One place is a value you can trust. Nine places is the answer to a discrepancy you have not investigated yet.
4
Confirm In Assurance, on a real device, before concluding anything.
Why Code shows intention. Assurance shows what actually left the phone, and only one of those is evidence.
✓ What you can now do

Recognise a function call, a string, a variable, a condition and a comment, which is enough to read a tracking call in any of the three languages you will meet. Check field names and fixed values against your specification without asking anybody. Spot the values that are decided elsewhere, and know those are the ones worth a question rather than a guess. Ask for a search instead of a snippet when the question is whether something exists. And describe problems without proposing patches, which keeps you on your own side of a line worth respecting.
