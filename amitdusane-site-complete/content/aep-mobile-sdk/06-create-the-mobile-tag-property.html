A mobile tag property looks like the web one and behaves nothing like it. On the web a property holds rules that run in the browser. Publishing changes what visitors execute within minutes. Here it holds no executable code at all. It holds configuration: which datastream to talk to, which extensions to switch on, what each is set to. The app fetches that configuration at launch. That is the one part of a mobile implementation that still behaves like the web.

Build it
1
Where Data Collection › Tags › New Property
Do Choose platform Mobile. A Web property cannot be used by an app, and the two are not convertible.
2
Do Install four extensions: Adobe Experience Platform Edge Network, Identity for Edge Network, Consent for Edge Network, and AEP Assurance. Mobile Core is always present and needs no installing.
3
Do In the Edge Network extension, select the matching datastream for each environment: the development datastream against Development, staging against Staging, production against Production.
4
Do Publish a library to Development. Until something is published, the environment exists but serves nothing.

The Edge Network extension will not work without Identity for Edge Network. Treat those two as one item, not two choices. Consent is separate, and deliberately so: a consent decision has to be expressible before any event is sent. Assurance earns its place by being the only way to see inside a compiled app.

Where this goes wrong

The property is created as Web rather than Mobile. It offers a plausible-looking set of extensions, none of which an app can load. The mistake surfaces only when a developer reports the SDK cannot find its configuration. A property's platform is fixed at creation, so the fix is a new one.

✓ Ready when

A Mobile property carries the four extensions, each environment points at its own datastream, and a library has been published to Development. The Development Environment File ID is now available under Environments, and that is the value a developer needs in Get the SDK into the app.
