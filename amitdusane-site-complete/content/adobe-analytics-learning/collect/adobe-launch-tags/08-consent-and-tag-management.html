A visitor in Germany opens your site. The consent banner appears, and they read it for about four seconds before clicking Accept.

Something happened during those four seconds. The page finished loading, the tag library initialised, and every rule you built became ready to fire. Whether any of them did, and what became of the data if they did, was decided long before this visitor arrived, by whoever configured the implementation. Possibly by nobody, because most of these settings have a default.

That gap is the whole subject. Consent is not a feature you switch on, it is a race between the page loading and the visitor deciding, and your job is to determine who wins it.

The four seconds before anybody clicks anything

Nothing about that window is unusual. Every consent implementation has one, because a banner cannot be answered before it is displayed, and a page cannot wait indefinitely for an answer that may never come.

What differs between implementations is what happens to the events that occur inside it.

The same four seconds, under three different settings

Read the three lanes and the trade becomes obvious. In keeps the most data and respects the least. Out respects the choice absolutely and permanently loses whatever happened first. Pending is the only one that defers the decision rather than pre-empting it, which is why it exists.

Consent is not a tag management feature, and that is the first thing to get right

A great many failed implementations begin with one misunderstanding: that consent is something the tag manager does. It is not. Three separate systems are involved, they own different jobs, and no one of them can do another's work.

Three systems, three jobs, and none of them overlap

Adobe states this boundary explicitly about its own tooling. The Opt-in service does not gather consent preferences and does not store them. It acts on a decision somebody else captured. Expecting Adobe to run your banner is the single most common way this goes wrong at the design stage, long before any code is written.

The three places you can enforce it

Given those three systems, there are three points at which a decision can actually be enforced, and they are not equivalent.

WhereHow it worksWhat it costs you
At the CMPThe consent platform blocks the tag from loading at allTotal control, but Adobe never initialises, so nothing is queued and nothing is recoverable
At the tag managerA rule condition reads the stored consent value and refuses to runFlexible and familiar, but it depends on the answer already existing when the rule evaluates
At the SDKThe library itself holds, drops, or sends events based on a declared consent stateHandles the waiting window properly, but it is a configuration nobody sees unless they look

Most real implementations use two of the three together, and that is correct rather than redundant. The CMP owns the visitor's answer, and the SDK owns the events that arrive before the answer does.

Why the rule condition is the fragile one

The tag manager approach is the one practitioners reach for first, because it uses machinery they already know. Rules makes the case for it directly: a condition reads the cookie holding the visitor's choice, and the rule becomes self-policing, running only when permission is present.

That reasoning is sound and the technique is genuinely useful. It also has a limit that is easy to miss, and the limit is timing.

A condition can only evaluate what exists at the moment it runs. On a first visit, at the instant a page-load rule fires, the visitor has not answered anything, so the cookie the condition is looking for is not there. The condition reads an absent value, treats it as no permission, and the rule does not run. Then the visitor clicks Accept four seconds later, and nothing goes back to collect the page view that was skipped.

⚠️ A rule that does not run leaves no evidence that it did not run

There is no error, no console warning, and no entry in any report. A skipped rule and a rule that never existed look identical from the outside, and the only visible symptom is a number lower than expected, which is indistinguishable from a quiet week. Consent conditions are worth testing on a genuinely fresh browser profile, because the second visit, when the cookie already exists, works perfectly and proves nothing.

The lesson is not that conditions are wrong. It is that a condition enforces a decision that has already been made, and something else has to handle the period before it was made.

The Web SDK answer: decide in advance what happens to events nobody has permitted yet

The Web SDK extension addresses the window directly, with a setting that declares what the library should do before it hears anything. It takes three values.

Default consentBehaviour before the visitor answersSuits
InEvents are collected normally. The library does not wait.Regions with no prior-consent requirement
OutNo request fires at all until consent changes to In. Anything in the window is gone.The strictest reading of an explicit-consent regime
PendingEvents are queued. On consent they are sent, on refusal they are discarded.Most explicit-consent implementations

Pending is the setting worth understanding properly, because it is the only one that does not force a choice between the data and the obligation. Nothing leaves the browser without permission, and nothing is thrown away before the visitor has spoken. If they accept, the queued page view is released and your first-page data survives. If they refuse, it is discarded and no request is ever made.

The value can also come from a data element rather than a fixed radio button, which is how one property serves several jurisdictions: pending for visitors in the European Union, in for regions where prior consent is not required.

ℹ️ The default is a posture, not a record

Adobe is precise that the default consent level is not written to the visitor's profile. It governs how the library behaves while it waits, and nothing more. The actual recorded consent comes from setConsent, which both updates the profile and creates a timestamped event describing the change. Confusing the two leads to teams believing they have a consent audit trail when all they have configured is a waiting-room policy.

The AppMeasurement answer: the Opt-in service

Implementations still running AppMeasurement and the Experience Cloud ID extension have a different mechanism, and it predates the Web SDK approach. The Opt-in service is a JavaScript library bundled with the ID service, exposed as adobe.optIn, and configured in Launch through its own extension rather than by hand.

Its distinguishing feature is granularity. Rather than one consent state for everything Adobe does, it gates each solution separately, so Analytics, Target and Audience Manager can be permitted independently. That maps neatly onto a banner offering categories rather than a single yes, because a visitor who accepts measurement but refuses personalisation is expressing exactly that distinction.

What it controls is cookie creation before consent, which is the specific thing an explicit-consent regime cares about. And as stated earlier, it does not gather or store the preference. It reads what your consent platform decided and acts accordingly.

The setting that is wrong by default for a large part of the world

Now the part that costs organisations real money, and it is a single radio button.

The permissive option collects events before the visitor has agreed to anything. It is the setting that produces complete data, it is the setting that makes a new implementation look like it is working, and for any jurisdiction requiring prior consent it is the wrong one. Adobe's own guidance for organisations needing explicit consent is to choose Out or Pending.

⚠️ Nothing tells you the setting is inappropriate for your visitors

The library does not know which jurisdiction a visitor is in, and it does not read your privacy policy. A permissive default produces clean, complete, entirely plausible reports while collecting data that was never permitted, and the reports are the only feedback most teams ever look at. Nobody discovers this by watching dashboards. It surfaces during a privacy review, an audit, or a complaint, at which point the collection has been running for months.

This is the same shape as the traps in Privacy and Data Retention, where a missing label produces a successful-looking response to a deletion request. The failure is silent, the reports look healthy, and the discovery mechanism sits outside analytics entirely.

What refusing consent does to identity

One consequence deserves stating on its own, because it explains report behaviour that otherwise looks like a bug.

Withholding consent generally means no cookie is written. No cookie means no persistent identifier, and no persistent identifier means the visitor cannot be recognised on the next page, let alone the next visit. Every page view becomes a first visit by a brand new person.

So a site with a strict consent posture and a large share of refusals will show unique visitors climbing, visits per visitor stuck near one, and multi-page journeys collapsing into single-page sessions. None of that is a tagging fault. It is the direct arithmetic of identity that was never allowed to persist, and the mechanism behind it is covered in Experience Cloud ID (ECID).

What you have now

Consent is a race, and the four seconds before a visitor answers are the part that implementations get wrong. Three systems share the work and none can cover for another: your consent platform asks and remembers, the tag manager decides whether to act, and the Adobe library decides what becomes of events that arrived before anybody had permission to collect them.

The rule condition is the tempting answer because it uses machinery you already know, and it is genuinely useful once a decision exists. It cannot help with the window before one does, and a rule that declines to run says nothing about having declined. That is what the library-level setting is for, and Pending is the value that refuses to choose between the obligation and the data.

Everything in this module has been about building an implementation that fires correctly. Consent is the layer that decides whether it is permitted to fire at all, which makes it the last thing to configure and the first thing anyone from legal will ask about.

What actually travels when permission is granted is a request carrying an identity, and that identity is the thread every report depends on. Experience Cloud ID (ECID) covers what that identifier is, where it lives, and why it is a great deal more fragile than it looks.

Where to find it in Adobe Launch

Web SDK consent: open the property, then Extensions > Adobe Experience Platform Web SDK > Configure > Consent, and set the default consent level or point it at a data element.

Recording a decision: build a rule with the Web SDK Set Consent action, triggered by your consent platform's own event.

AppMeasurement path: install the Opt-in extension alongside the Experience Cloud ID extension and enable the solutions you need to gate.
