Why it matters to you

Your tracking lives inside a page built from three languages. A tag manager finds buttons and links by reading that page. When a developer changes the page, your tracking can stop without any error. Knowing what each language does is how you see that coming.

Three languages, three jobs

Think of a house. HTML is the structure: the walls, the doors and the rooms. CSS is the decoration: the paint, the furniture and the lights. JavaScript is the electricity, which makes the doorbell ring and the lights turn on.

A house can stand without paint, and a page can show without CSS. It just looks plain. A page without JavaScript still shows its text, but nothing on it reacts, and no tracking runs, because tracking is JavaScript.

Here is one button written in all three languages.

<!-- HTML: what the button is -->
<button id="buy" class="btn-primary" data-track="add-to-cart">Add to cart</button>

/* CSS: how it looks */
.btn-primary { background: green; color: white; }

// JavaScript: what happens when it is clicked
document.getElementById("buy").addEventListener("click", addToCart);

You do not need to write any of these lines. You only need to recognise which language you are looking at, because each one is changed by different people for different reasons.

The DOM is the page your tracking sees

The browser does not keep the HTML file as it arrived. It reads the file and builds a live model of the page called the DOM, short for Document Object Model. Every heading, link and button becomes an element in that model.

JavaScript changes the DOM all the time. It adds a product to a list, opens a pop-up, or fills in a price. The HTML file on the server stays the same. That is why the source of a page and the page on your screen can disagree. The page source shows the file the server sent. The browser's developer tools show the DOM as it is now.

Your tag manager reads the DOM, not the file. So what matters is what is on the page at the moment the tracking runs.

How a tag manager finds a button

Elements carry labels called attributes. Three of them matter to tracking. An id is a unique name for one element. A class is a label for styling, and many elements can share it. A data attribute is a custom label that starts with data-.

A CSS selector is a short pattern that finds elements by those labels. Tag managers use selectors to decide which clicks to track.

#buyThe one element whose id is buy. Stable, if the developers treat ids as fixed.
.btn-primaryEvery element with that class. Fragile, because classes change with the design.
[data-track]Every element with a tracking label. The most stable, because it exists only for tracking.

Why a redesign breaks click tracking

Classes exist for designers. When a designer renames btn-primary to button-main, the visitor sees no difference. The rule that looked for .btn-primary now finds nothing, and no error appears anywhere.

Where this goes wrong

A click rule finds a button by its class. A redesign renames the class. The site looks the same, the rule matches nothing, and the click report drops to zero on the day of the release. The drop is read as a change in customer behaviour.

The fix is to ask developers for data attributes that exist only for tracking, such as data-track="add-to-cart". Designers leave them alone, because they change nothing on screen. How rules use these selectors is covered in Rules.

Elements that arrive late

Some elements are not in the HTML at all. JavaScript adds them after the page loads: a pop-up, a list of products that grows as you scroll, a form inside a drawer. A rule that looks for an element when the page loads cannot find one that arrives later.

So before you ask for a click to be tracked, ask whether the element is in the page from the start or added later. The answer decides how the tracking has to be built. Sites that change the whole screen this way are covered in Single-page apps.
