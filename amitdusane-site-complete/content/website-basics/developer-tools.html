Why it matters to you

Most tracking questions start the same way: was the call sent, and what did it carry? The answer is on your own screen in under a minute. Checking before you raise a ticket turns "the numbers look wrong" into "this call is missing this value", which a developer can act on.

Opening them

Every desktop browser has developer tools built in. Press F12 on Windows, or Cmd+Option+I on a Mac. You can also right-click anywhere on a page and choose Inspect. In Safari, first turn on the Develop menu in the settings.

The tools open as a panel with several tabs. Four of them do almost all of your work.

ElementsThe DOM, the live page. Use it to find an element's id, class and data attributes.
ConsoleScript errors in red, and a line where you can type JavaScript to ask the page a question.
NetworkEvery request the page sends, in order. Your tracking calls are here.
ApplicationCookies and stored values. Firefox calls this tab Storage.

Finding your tracking call

Open the network tab before you load the page, because it only records requests made while it is open. Then load the page and type a filter into its search box. The filter depends on how the site sends data to Adobe.

b/ss       classic Adobe Analytics (AppMeasurement)
interact   Adobe Web SDK
collect    Adobe Web SDK, for calls sent as a page closes

Click a request to open it. The headers show the full address and the status code. The payload shows the data the call carried, which for a tracking call means your variables and their values. Read them there, value by value, against what you asked for.

A success code is not the whole story

A status of 200 or 204 means the request reached Adobe. It does not mean the data was kept or reported the way you expect, because rules on Adobe's side can still change or remove it. The network tab proves what left the browser, and nothing after that.

Keep the log when the page changes

When a click takes the visitor to a new page, the network tab normally clears its list. The call sent on that click disappears with it, and it looks as if no call was sent at all.

Tick Preserve log at the top of the network tab. Firefox calls it Persist Logs. The list then keeps every request across page changes. Leave it ticked whenever you test links, forms and anything else that leaves the page.

The console, for errors and quick questions

Red lines in the console are script errors. One error can stop every script that runs after it, including tracking. When a call is missing, look here before anything else.

You can also ask the page questions. Typing adobeDataLayer and pressing Enter shows the Adobe Client Data Layer on sites that use it. Typing _satellite.buildInfo on a site with Adobe Tags shows when the loaded tag library was built. Anything you type there affects only your own browser.

The Application tab shows what the site remembered

The Application tab lists every cookie the site has set, with its domain and expiry date. Adobe's visitor ID cookies appear there with names that start with AMCV_ or kndctr_.

You can delete cookies from this tab to test as a brand-new visitor. What those cookies are, and why browsers delete them, is covered in Cookies and browser storage.

What these tools cannot tell you

Developer tools show what left your browser. They cannot show what Adobe did with the data after it arrived. A call can be perfect and the report still wrong, because processing rules and other settings change data on its way into reports.

When the call is right and the report is not, the problem has moved to Adobe's side. The next question is for whoever manages the report suite, and you can now show them exactly what was sent.
