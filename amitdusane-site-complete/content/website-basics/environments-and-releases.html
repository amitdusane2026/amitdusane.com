Why it matters to you

You will often be asked to check tracking before a release. Whether that check means anything depends on which copy of the site you checked. Testing the wrong copy is the most common way a tracking fault reaches the live site after it was approved.

Three copies of one site

Developers keep several working copies of a website, each called an environment. Most teams have at least three.

Think of a play. Development is the rehearsal room, where actors try things and make mistakes. Staging is the dress rehearsal on the real stage, with costumes and lights but no audience. Production is opening night, in front of real people.

Each environment has its own address, such as dev.example.com, staging.example.com and www.example.com. The names vary. You may also hear QA, test or UAT, which are all kinds of staging.

How a change moves

A developer writes a change in development. The change is then copied to staging, which is called a deploy. Testers check it there, and so do you. Finally it is deployed to production, and real visitors see it.

Many teams release to production on a fixed schedule, such as every two weeks. If a release goes wrong, the team can put the previous version back, which is called a rollback. A rollback removes your tracking change too, if it was part of that release.

Released is not the same as switched on

Many teams hide new features behind a switch called a feature flag. The code goes to production with the release, but the feature stays off until somebody turns it on, sometimes for a small share of visitors first.

So a release date and a launch date can be weeks apart. Tracking for a new feature can be live in production and still send nothing, because no visitor can reach the feature yet. When the flag is turned on for some visitors only, the numbers grow in steps.

Ask two questions about any new feature: when is the code released, and when is the flag turned on, and for whom? Plan your checks for the second date, not the first.

Staging is close to production, never identical

Staging is built to behave like the live site, but it is not the live site. It usually has test products and fake orders. Payments go to a test account. Search engines are kept out. Some services it connects to are test versions.

Tracking on staging should also send its data to a separate report suite, so test visits never mix with real ones. So a test on staging proves that the logic works. A short check on production after the release proves that it works for real visitors.

The tag manager has its own copies

Adobe Tags keeps development, staging and production libraries, each with its own embed code. The site's staging copy should load the staging library, and production should load the production library.

Where this goes wrong

The staging site loads the production tag library. Testers click through the checkout all week, and their test orders arrive in the real report suite. The revenue report for that week includes hundreds of orders nobody paid for.

How those libraries move from one environment to the next is covered in Environments and Publishing Workflow.

Your part in a release

Before the release, test on staging and write down exactly what you checked. After the release, check production the same day with the network tab open. The next morning, compare the numbers with the day before.

Ask for the date and time of every release that carries a tracking change. Without that moment, nobody can separate a change in the data from a change in the site. How to look inside the pages you test is covered in Developer tools and the network tab.
