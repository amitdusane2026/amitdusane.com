Why it matters to you

A website's tracking passes through several hands: developers, the owner of the tag manager, sometimes an agency, and you. Each can do their part correctly and the result can still be wrong, because nobody owned the places where the parts meet. Knowing who owns what, and what each person needs from you, is most of what gets tracking delivered on time.

Who usually owns what

DevelopersThe page, the data layer, the embed code and any hard-coded tracking.
Tag manager ownerRules, data elements, other companies' tags and publishing. Often the analytics team.
YouThe business question, the specification, the variables, and checking the data.
MarketingCampaign links and the codes inside them.
Legal or privacyWhat consent is needed, and for what.

Names differ between companies, and one person can hold several of these roles. What matters is that each part has one named owner.

The specification is your half of the agreement

Think of having a kitchen built. The carpenter builds exactly what the drawing shows. A vague drawing produces a kitchen that matches the drawing and not the one you needed.

Your drawing is the specification: every event, the exact moment it fires, every value it carries, an example of each value, and where each value comes from. Developers build from it, so everything you leave out is something they have to guess. How to build one is covered in What Is an SDR.

A ticket a developer can build

Developers work from a ticket, one request in a tracking system such as Jira. A good tracking ticket answers four things.

  1. What: the values to add to the data layer, with their names.
  2. When: the exact moment, such as when the order confirmation screen has loaded.
  3. Example: the object you expect, written out in full.
  4. Done means: the checks that decide whether the work is finished.
window.adobeDataLayer.push({
  event: "purchase",
  order: { id: "ORD-55120", total: 128.40, currency: "EUR" }
});

The last point is the acceptance criteria, and it matters most. Write it before the work starts, for example: one purchase event per order, the total as a number, after discount. Then everyone agrees in advance what finished looks like.

When work actually happens

Most development teams plan their work in a sprint, a fixed period that is often two weeks. Work is chosen at the start of the sprint. A ticket that arrives in the middle usually waits for the next one.

Before a release there is often a code freeze, a few days when no new changes are accepted. So ask for two dates early: when the next sprint is planned, and when the next release goes out. Then work backwards from them.

Keep your own record

Write down every tracking change with three facts: what changed, when it reached production, and who asked for it. Keep the list where the people who read your reports can find it.

A year from now, somebody will ask why a number jumped in March. Without a record, the answer depends on who still remembers. With one, it takes a minute. Analysis Workspace lets you attach a dated note to your reports for this reason, and a shared list of changes does the same job for the whole team.

The part only you can check

Developers test that their code runs. The tag manager owner tests that the rule fires. Only you know whether the value is right for the question the report must answer.

Where this goes wrong

The developer confirms the data layer holds a price. The tag manager owner confirms the rule sends it. Nobody checks that it is the price before the discount, not after, and revenue is overstated for a whole quarter.

So check the values yourself after every release, on the live site, as described in Development, staging and production. It is the one check nobody else is in a position to make.
