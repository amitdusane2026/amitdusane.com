Why it matters to you

Some tracking changes take you ten minutes. Others wait for a developer and a release. Knowing which is which is the difference between promising a date and promising a week, and it tells you who to ask before you ask anyone.

What a tag manager is

A tag is a piece of code from another company, such as an analytics or advertising script. A tag manager is a tool that loads and controls all of those tags from one place. Adobe Tags and Google Tag Manager are the two you will hear most.

Think of a noticeboard in a shared office. The building team fixes the board to the wall once. After that, anybody with the key can pin up notices without calling the builders. The board is the tag manager, and the notices are your tracking.

Fixing the board to the wall is the embed code: one line a developer adds to every page so the tag manager can load. Everything the tag manager does after that is set up inside the tool, not in the site's code.

What the tag manager can do alone

Inside the tag manager, a rule says: when this happens, do that. A data element is a named value the tag manager reads from the page, such as the page name or a product ID. With those two, the tag manager can:

  • send page views, and track clicks on elements that already exist on the page
  • read values that are already on the page, in the address, in a cookie or in the data layer
  • decide which variable each value goes into, and change that later
  • add, remove or pause tags from other companies

All of this can be changed and published the same day, usually by the team that owns analytics. How it is organised is covered in Launch Architecture.

Where the embed code sits matters

The embed code usually sits in the head of every page, the part the browser reads before the visible content. Developers often load it in a way that does not hold up the rest of the page. The page is faster, and the tag manager may start a moment after the page has begun.

Anything that happens before the tag manager starts is invisible to it. A very fast click, or a value the page sets and then removes, can be missed. So if a tracking problem only happens on quick clicks, or only on the first page of a visit, ask where the embed code sits and how it is loaded.

What only the site's code can do

A tag manager can only work with what the page already contains. It cannot invent information the page does not have, and it cannot react to moments the page does not announce.

Tag managerTrack clicks on the Buy button. Move a value from one variable to another. Add a new tag from another company.
Site codeTell tracking whether the customer is signed in. Send the order total from the server. Announce each screen change in a single-page app.
BothThe site puts a value in the data layer, and the tag manager sends it.

The quick test: if the value or the moment is not visible anywhere on the page today, it needs a developer.

The data layer is where the two meet

The data layer is an agreed place on the page where the site puts values for tracking to read. Developers fill it, and the tag manager reads it. Once it holds the right values, most later changes are tag manager work only. What goes into one is covered in What Is a Data Layer.

Watch for hard-coded tracking

Some tracking is hard-coded, which means it is written directly into the site's code instead of the tag manager. Older sites often have some, usually on a few important pages. A tag manager cannot change it, and it cannot see it.

Where this goes wrong

Page views on the checkout are counted twice. The rule in the tag manager looks correct. Years ago a developer added a tracking call to the checkout template, and both have run on every checkout page since.

So when a number is doubled, ask whether anything is hard-coded before you change a single rule. The answer takes one question to a developer, and it can save a week of changing rules that were never the problem.
