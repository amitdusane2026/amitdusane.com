Why it matters to you

Classic tracking counts a page view each time a page loads. A single-page app loads only once. Without extra work, a visitor who looks at ten screens is counted as one page view, and everything they did after the first screen is credited to the wrong page.

One load, then the screen changes

In a multi-page site, every click asks the server for a new page. The screen goes blank for a moment and the new page is built from the start.

In a single-page app, the first request brings the whole application, most of it JavaScript. After that, a click does not ask for a new page. JavaScript replaces the content on the screen and changes the address in the address bar. To the visitor, it looks like a new page. To the browser, nothing loaded.

Think of a book and a slideshow. In a book you turn to a new page. In a slideshow the frame stays and only the picture changes. A counter that counts page turns works for the book, and stays at one for the whole slideshow.

How developers build them

Most single-page apps are built with a framework, a ready-made toolkit that handles the screen changes. The names you will hear most are React, Angular and Vue, and Next.js, which is built on React.

Each screen of the app is a route, and every route has its own address, such as /checkout. When the route changes, the framework updates the address through the browser's history. That update is the history change, and it is the one signal every single-page app gives without extra code.

Telling in one minute

  1. Open the browser's developer tools and choose the Network tab.
  2. Choose the filter for documents, usually called Doc.
  3. Click a link inside the site.
  4. If the address changed and no new document appeared in the list, you are in a single-page app.

Many sites mix both kinds. The shop is a normal site, and the checkout is a single-page app. Check the part of the site you are asking about, not just the home page.

What has to be added

Somebody has to tell the tracking that the screen changed. The page view it then sends is called a virtual page view, because no real page loaded. There are two common ways to trigger one.

History changeThe tag manager listens for the address to change. No developer work, but it can fire before the new screen's values are ready.
A site eventThe site sends its own event once the new screen and its values are ready. It needs a developer, and it is reliable.

Ask for the site event. The history change is tempting because it costs nothing today, but it often reports the new address with the old screen's values. How Adobe Analytics handles these screens is covered in SPA Tracking.

Values that stay behind

On a normal site, each page starts clean. In a single-page app the page never reloads, so values set on one screen can still be there on the next. A search term, a product name or an error message can travel forward and be reported again on screens where it does not belong.

Where this goes wrong

A visitor views a product and then opens the basket. The product name from the product screen is still set, so the basket view is reported against that product. It happens for every visitor, and the product looks far more popular than it is.

So the tracking must clear old values before it sends each new screen. Ask the developer how values are reset between screens, then check it yourself by moving between two screens with the network tab open.
