Why it matters to you

Your reports are organised by address. Page names, campaign codes, referrers and site sections often come from parts of a URL. When you can name each part, you can say which part a problem lives in, and who can fix it.

Five parts, read from left to right

Every web address has the same parts in the same order. Take this one:

https://shop.example.com/women/shoes/?cid=em_summer&utm_medium=email#reviews

Protocolhttps:// is how the browser talks to the server. The s means the connection is encrypted.
Domainshop.example.com names the site. shop is a subdomain of example.com.
Path/women/shoes/ names one page on that site.
Query stringEverything after the question mark. Here it holds two parameters.
Fragment#reviews points to a place on the page.

Think of a postal address. The domain is the building, the path is the flat number, and the query string is a note written on the envelope. The fragment is a sticky note you keep for yourself. It never goes in the post.

The domain decides who can read what

Browsers keep cookies by domain. A page on shop.example.com can read a cookie set for example.com. A page on another domain cannot, even when your company owns both.

That rule is why a visitor who moves from example.com to example-travel.com can arrive in your reports as a new visitor. The same person walked from one building into another, and the second building has never seen the ticket from the first. How to join the two is covered in Cross-Domain Tracking.

The query string is where campaigns live

The query string is a list of parameters. Each one is a name and a value joined by an equals sign, and parameters are joined to each other by &. Marketing teams put campaign codes there, such as cid=em_summer.

Parameters are easy to lose. A redirect can drop them. A person can copy a link without them. A form can send the visitor to a new address that does not carry them. Each of these turns a campaign visit into direct traffic, and none of them shows an error.

Some characters cannot sit in an address as they are, so they are written as codes. A space becomes %20 or a plus sign. When a campaign code looks strange in a report, check whether it was written with spaces or other special characters.

The fragment never reaches the server

Everything after the # stays in the browser. It is not sent to the server, and it is not included in the referrer that the next page receives. Pages use it to jump to a heading, which is why a link ending in #reviews scrolls straight to the reviews.

Some older single-page apps use the fragment to change screens, with addresses such as example.com/#/checkout. Anything that reads the address on the server sees only example.com/ for every screen. Tracking has to read the fragment in the browser instead. More on these sites is in Single-page apps.

The referrer is the address before

When a visitor clicks a link, the browser usually tells the next site where the visitor came from. That address is the referrer, and your reports use it to decide whether a visit came from search, from another site or from nowhere.

Browsers now send less of it. When a visitor moves between two different sites, most browsers send only the domain of the previous site, not its path or query string. So a report can know that a visit came from a search engine without knowing what was searched. Some links also tell the browser to send no referrer at all, and those visits arrive as direct traffic.

Many addresses, one page

Servers often show the same page at several addresses: with and without www, with and without a slash at the end, with and without tracking parameters. A report that stores the full address splits one page into many rows.

That is why most implementations set the page name on purpose instead of copying the address. When two rows in a report look like the same page, compare the two addresses character by character. The difference is almost always in one of these five parts.
