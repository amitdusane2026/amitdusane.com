Why it matters to you

Everything an iPhone app needs happens inside one program called Xcode. Knowing what that program does explains most of what you will find slow, and most of what you can change without waiting for anybody.

Xcode does the job of five systems you already use

Xcode is Apple’s development program. It is free, and every iPhone app in the world is built in it.

Think about what publishing a change to a website touches. Somebody edits code in an editor. Configuration values sit somewhere else, in a settings file. A build system packages it. Tags and tracking are published from Adobe’s interface, on their own schedule. A web server serves the result. That is five systems, five logins, and you personally hold two or three of them.

On iPhone, those five jobs are one program. The code is edited in Xcode. The configuration sits in the same project folder. The build runs in Xcode, on somebody’s actual machine. The signing happens there, which is Apple’s proof that the app really comes from the company it claims to. The upload to Apple happens there too.

That one arrangement explains most of what you will find slow. A tracking name, a button colour and a rewrite of the payment flow all leave the building by the same route: edit, build, sign, submit, wait for Apple to review. There is no fast lane for small changes, because nothing in the system knows that a change is small. Six characters and six thousand lines cost the same to ship.

✓ The one exception, and it is yours

Everything the mobile tag property controls is fetched by the SDK while the app is running, rather than built into the app. Turning a setting on, changing a datastream, or adjusting the tag property reaches installed apps within minutes and needs no release at all. Configuration travels freely. Anything that needs a new line of code in the app does not.

Swift, and reading four lines of it

The language is Swift. Apple introduced it in 2014 to replace an older language called Objective-C, which is older than the iPhone. You will still meet Objective-C in long-lived apps, and most teams work in both.

You are never going to write Swift. You are going to be shown it, pasted into a ticket. Reading four lines with confidence changes the conversation you can have about them.

MobileCore.setLogLevel(.debug)
MobileCore.initialize(appId: "a1b2c3d4e5f6")

Two things in that code do most of the work.

The dot means belongs to. MobileCore is a part of the SDK. initialize is something MobileCore can do. So you read the line left to right, like a sentence: this thing does that.

The label in front of a value. In appId: "a1b2c3d4e5f6", the word appId is not a comment and you cannot leave it out. It is part of the function’s real name.

This is why Swift reads almost like English. It is also why searching the code for the bare word initialize often finds nothing useful.

Target, configuration, scheme

These are the three words worth learning by heart. A developer will use all three in one sentence without noticing that none of them means anything to you yet.

An Xcode project rarely produces one app. It produces a family of things from one body of code.

TargetA thing that gets built: the app, a home screen widget, a watch app, an internal staff version. Each is a separate program once built.
ConfigurationA named set of build settings. Almost every project has at least Debug and Release.
SchemeWhich target, built with which configuration. It is the dropdown at the top of the Xcode window.

An SDK added to one target is not in another. That is the honest answer to why the widget has never reported anything.

The reason to remember all three is the Environment File ID, which you give the developer in Get the SDK into the app. It very often differs by configuration, which is correct: Debug points at development, Release points at production, so the two report to different places.

When test traffic appears in the report the business is watching, one question settles it. Which scheme, and which configuration, produced this build? Asking it in those words also tells the developer the conversation will be short.

Info.plist, and the one entry that is yours

Every iPhone app carries a file named Info.plist. It is the app’s declaration of itself: the display name, the version number, the screen orientations it supports, and the reason it gives for each sensitive thing it wants to use. Nearly all of it belongs to engineering.

One entry is yours in everything but the typing. It is the sentence in the App Tracking Transparency prompt, the dialog that asks permission to track the user across other companies’ apps and websites.

That sentence is a marketing decision, not an engineering one. More people read it than any other string the company writes, and it is very often still the placeholder a developer typed in a hurry.

What that prompt actually controls

This is the most commonly overstated thing in mobile measurement, so it is worth stating precisely.

Declining the prompt withholds the advertising identifier. That matters for install attribution and for measuring paid campaigns.

It does not switch off analytics, and it is not the same decision as the consent you configure in Handle consent. The ECID, lifecycle metrics, screen views, actions and everything else this guide implements continue exactly as before, because none of them use that identifier.

A team that believes otherwise will either panic about a number that was never at risk, or quietly over-scope its consent language. Both are expensive.

Where this goes wrong

The tracking permission prompt ships with engineering placeholder text that nobody in marketing ever saw. Every new user reads it on first launch, people quote it in App Store reviews when they dislike it, and changing it needs a release like anything else. Ask to read that sentence before the first submission, not after.

Where startup lives

The SDK has to be started once, early, before anything tries to send an event.

For most of the platform’s history that meant one place: a file called AppDelegate, and a method inside it that runs once the app has finished launching. Many production apps still work exactly that way.

An app built more recently with SwiftUI, which is Apple’s newer way of describing screens, may have no AppDelegate at all. Its starting point is a small structure marked @main. Both arrangements are correct and both are common, so “put it at startup” no longer points at a single file.

What you need is narrower than the file name, and it works either way. Starting the SDK must finish before the first screen appears. An event fired before the SDK is ready is not queued and not retried. It is simply gone, and it leaves nothing behind for you to find.

So ask whether the SDK starts before the first screen. That question beats asking which file it sits in, and it catches the fault that actually happens.
