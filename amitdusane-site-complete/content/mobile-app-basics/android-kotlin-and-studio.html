Why it matters to you

Most of what you will ever need from an Android developer is one of three files or one line from a log. If you know their names, a meeting becomes a message, and a problem that takes a week to find takes a minute.

Android Studio, and a build file you can read

Android Studio is Google’s tool for making Android apps. Code is written there, the app is built there, and it is signed and uploaded to the store from there. It does the same job Xcode does for iPhone apps.

One difference helps you. On Android the build settings live in Gradle files. Gradle is the tool that builds the app, and its files are plain text, stored with the code, and readable by anybody.

So a developer can paste you the exact lines that add the Adobe SDK, and you can read them without opening anything. Ask for the Gradle block by name and you will usually get it in a reply rather than in a meeting.

Kotlin, and two things you will see everywhere

The language is Kotlin. Google made it the main language for Android in 2019, replacing Java. Java is still there in older apps, and developers move between the two easily.

val and var. A val is set once and never changes. A var can change later. So if you see val, the value is fixed.

A question mark after a type. String? means the text might be missing, and Kotlin forces the developer to say what happens when it is. You will see question marks on identity and consent values, because those really can be missing while the SDK is still starting.

The manifest is not one file

Every Android app has a file called AndroidManifest.xml. It is the app’s description of itself: its screens, its services, the permissions it asks the phone for, and the code that runs first.

Here is the part that confuses people. The manifest in the developer’s project is not the finished one. Every library the app uses brings a small manifest of its own, and when the app is built, Gradle merges them all into one. That merged manifest is what goes into the app and what the phone reads.

So a library can add a permission without anybody on the app team writing a line. The Adobe SDK does exactly that: its Core library adds android.permission.INTERNET and android.permission.ACCESS_NETWORK_STATE, because it has to reach the network and check the connection.

✓ Ask for the merged manifest

When a privacy or legal team asks which permissions the app uses, the project file will understate it, because it does not show what libraries added. Ask the developer for the merged manifest by that name. Android Studio produces it in seconds, and it is the only version that matches what a phone receives.

How the SDK finds its own extensions

One line starts the whole SDK, and it names no extensions at all.

MobileCore.initialize(this, "YOUR_ENVIRONMENT_FILE_ID")

The merged manifest is what makes that work. Each Adobe library adds a note to it naming its own extension, and on startup the SDK reads those notes and loads what it finds. So the extensions that run are exactly the libraries in the app, and there is no second list to fall out of date.

It also gives you a quick check. At debug log level the SDK writes one line for each extension it finds, starting Discovered extension:. Ask for those lines and count them against what you asked for in the ticket.

Build type, flavour and variant

One set of Android code can produce several versions of the app. Two words describe them, and a third combines them.

Build typeDebug or release. Decides logging, speed, and often which Adobe property gets the data.
FlavourOptional. Different editions from one set of code, such as one per brand.
VariantThe two combined, such as brandaRelease. The exact answer to “which app am I looking at”.

The Environment File ID is often set per variant, so each brand reports to its own place. When test data appears in a live report, asking which variant produced the build usually settles it in one reply.

Where startup lives, and the silence when it is missing

An Android app has one usual place for code that must run before anything else: a class that extends Application, with the startup work in its onCreate method. Starting the Adobe SDK belongs there.

Writing that class is not enough. The manifest has to point at it, through an android:name attribute. Without that line, Android quietly uses its own default class instead. The SDK never starts, and not one event is ever sent.

Where this goes wrong

A reviewer reads the change, sees the startup code exactly where it was asked for, and approves it. The line in the manifest was never added. Weeks later the report is empty and the code still looks correct to everybody who opens it. When an Android app sends nothing at all, check that the manifest names the Application class before you check anything else.
