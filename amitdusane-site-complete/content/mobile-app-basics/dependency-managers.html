Why it matters to you

Nobody copies the Adobe SDK into an app. They write down its name and a version, and a tool fetches it while the app is being built. That is why two builds from the same code can contain different versions of the SDK.

A list, not a parcel

The Adobe SDK is not copied into the project. What goes into the project is a list, and that list names each library the app needs.

When somebody builds the app, a tool reads the list, downloads each library from a public store, and joins the results into the build. The libraries are not kept next to the company’s own code. They arrive fresh every time anybody builds.

That tool is called a dependency manager, and every serious project has one. Think of a shopping list rather than a delivery. The list lives in the code, gets reviewed, and can be argued about. The goods come from somewhere else, at the last moment.

This is completely normal and it is not a weakness. It is how almost all modern software is put together.

One result matters to you straight away. Two developers can build from identical code and finish with different libraries inside their apps. That happens whenever the list leaves any freedom about which version to fetch. The code was the same and the list was the same. What the list resolved to was not, and nothing announces it.

Three tools doing one job

Three names come up, and the differences between them matter far less than the job they share.

Swift PMApple’s own, built into Xcode. The current default on iPhone.
CocoaPodsOlder, was the iPhone standard for years, still in many working apps.
GradleAndroid. Handles libraries and is the build system itself.

All three read a list of libraries, fetch them, and make the versions fit together. Which one a project uses was decided years ago. That choice changes the file a developer opens and the command they run. It changes nothing you will ask for, and nothing about how the Adobe SDK behaves once it is in there.

The SDK is not one library

This is the fact that makes versions matter. The Adobe Mobile SDK is a set of libraries, usually six or seven in a working implementation. They are built, tested and released together.

Core is one. Identity is another. So are Lifecycle, Signal, the Edge extensions and the Assurance extension. Each is a separate library with its own version number, listed separately and fetched separately.

Each one expects the others to come from the same release, because that is the only combination anybody tested. They are parts of one product that happen to be delivered as several parcels.

Mix versions from different releases and one of two things happens.

Build failsThe good outcome. Somebody has to deal with it before anything can ship.
Build worksThe bad outcome. The app behaves strangely weeks later, as a data problem with no obvious cause, and nobody connects it to a dependency file edited during different work.

The bill of materials

Adobe solves this on Android with a bill of materials, published as sdk-bom. It is a single line naming a combination of every library in the set that is known to work together. Each Adobe library listed after it takes its version from that combination, which is why those lines carry no version numbers of their own.

implementation platform('com.adobe.marketing.mobile:sdk-bom:3.+')
implementation 'com.adobe.marketing.mobile:core'
implementation 'com.adobe.marketing.mobile:identity'
implementation 'com.adobe.marketing.mobile:signal'
implementation 'com.adobe.marketing.mobile:lifecycle'

You can see the arrangement without knowing Gradle. The first line pins the set. The four lines after it name members of the set and give no version at all, because the first line already decided for them.

Adding a fifth extension later means one more line with no version on it. It cannot drift away from the others, because it has no separate number to drift.

On iPhone the equivalent is one consistent version range across all the Adobe packages. The mechanism differs and the principle does not: one decision about versions, made once, in one place. The alternative is seven decisions made on seven different afternoons by people who were each solving something else.

Adobe’s example uses 3.+, which means the newest release of version three. That is a reasonable default and not the strictest option. The + moves, so two builds a month apart can honestly resolve to different versions. A team that needs to rebuild an old version exactly will pin a fixed bill of materials instead and raise it deliberately. Ask for that on anything subject to audit.

Reading a dependency block without knowing the language

Ask a developer to paste the Adobe lines from the dependency file. It takes them about ten seconds. Then read the shape of what comes back, not the syntax, and look for three things.

GoodA bill of materials line, or on iPhone one version range covering everything. Somebody has thought about this and the set will stay coherent by itself.
WeakSeven Adobe lines each carrying its own version number. The set will drift the first time one of them is updated alone.
AskVersions that visibly disagree, a five on one line and a three on another. That is worth a question now rather than a week of debugging later.

That is the whole skill, and it is smaller than it sounds. You are not auditing the build or second-guessing an engineer. You are checking that one decision was made on purpose rather than by accident.

Where this goes wrong

An extension is added months after the original work, pinned manually to whatever version was current that week. Everything builds and the app ships. The mismatch appears later as behaviour nobody can reproduce: events arriving sometimes, or an extension that registers on one platform and not the other. The dependency block held the answer the whole time, and nobody outside the mobile team had ever looked at it.
