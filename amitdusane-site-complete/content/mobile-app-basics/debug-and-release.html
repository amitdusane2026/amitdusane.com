Why it matters to you

A developer saying “it works on mine” is usually telling the truth about a build that nobody else will ever run. Customers run a different build, and that is the one your numbers come from.

One set of code, two apps

Every project produces at least two kinds of build from one set of code. A debug build is what a developer runs while working. A release build is what goes to a store.

They come from identical files and they are not identical programs, because the instructions given to the compiler are different.

DebugLogging kept, so a developer can watch what the app does. Little optimisation, so it compiles fast and runs slowly. Usually points at test services.
ReleaseLogging removed. Heavily optimised, so work is rearranged and anything unnecessary is dropped. Signed for the store and pointed at production.

Every one of the debug choices exists to make the app easier to inspect while it is being worked on, and all of them are correct for that. But the release build is the only one that ever reaches a customer, or produces a number your business acts on.

The dress rehearsal

A rehearsal is the same play, the same cast and the same script. It also has the house lights half up and a prompter you can hear from the wings. The director can stop everything and take a scene again. Everybody knows the conditions are generous, and that is the point of holding one.

Opening night removes all of it at once. The play has not changed. Anything the prompter was quietly covering is now exposed, and there is no way to stop.

That is the relationship between the two builds. The logging a developer reads is the prompter. The relaxed timing of an unoptimised build is the pause while somebody finds their place. Both disappear on the night, and neither says in advance what it was covering.

Three ways the difference bites

Most of the time the two builds behave identically, and that is what makes the differences dangerous. A difference that appeared every time would have been found years ago. These appear occasionally: often enough to reach production, rarely enough to survive testing.

1. Optimisation changes timing. A release build runs faster and reorders work that a debug build did in a leisurely sequence. Code can contain a race, where two things assume an order nobody actually guaranteed. That code works for years in debug and fails in release. The version that costs you events is the SDK starting up while the first screen is already drawing. An event fired before the SDK is ready is not queued and not retried. It is gone.

2. Removed logging takes the evidence with it. The log lines a developer relied on to prove the tracking worked are not in a release build. So the build you most need to understand is the one that tells you least about itself. Unless validation was planned around that from the start, the natural response is to go back to a debug build, and the whole problem repeats.

3. The two builds usually report to different places. This is the one that produces wrong numbers rather than missing ones, and it deserves its own section.

Where the test traffic goes

The SDK is told which Adobe property it belongs to by an Environment File ID. That value very often differs between debug and release, and that is deliberate rather than a mistake. Development traffic should land in a development environment and production traffic in production.

It also means the build a developer validates on and the build the business reports from point at two different places. Everything can look perfect in the development environment for weeks while the production configuration carries a value nobody has checked.

The failure runs the other way too, and that version is more embarrassing. A build configured to report to production gets passed round the office for two weeks of testing, and quietly fills the report the business is watching with staff traffic. Nothing errors. The numbers simply include forty people who were never customers and who all behave like unusually thorough shoppers.

On iPhone this value is usually decided by the build configuration, which is one of the three words in iOS: Swift, Xcode, and what your developer is looking at. So asking which configuration produced a build is the same question as asking where its data went, phrased in the words the person answering already uses.

Where this goes wrong

An implementation is approved from a debug build, on a developer’s machine, pointed at the development environment. Every event is correct. The release build carries a placeholder Environment File ID that was never updated, and reports nowhere at all. Nobody finds out until somebody opens the production report after launch, and by then the fix needs another release and another store review.

The only build worth approving

Final validation happens on a release build, and on nothing else. Not a debug build with logging turned down. Not a release-signed debug build either, which sounds close enough and is not. An actual release build, ideally the exact file intended for the store. That validation is Validate in Assurance.

Both platforms give you a way to get one before the public has it. Apple has TestFlight. Google Play has internal and closed testing tracks. Both send a genuine release build to a named list of people, which is the whole reason they exist.

Validating there costs something, and it is better said now than discovered mid-project. Logging is gone, so you read Assurance instead of a developer’s console. Each attempt needs a build rather than a quick rebuild on somebody’s machine. That is the price of testing the thing that ships instead of a rehearsal of it, and it is worth paying once at the end rather than never.
