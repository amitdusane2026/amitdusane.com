Why it matters to you

You will never write Swift or Kotlin. But a developer will paste four lines into a ticket, and reading them with confidence settles questions that would otherwise need a meeting.

What you are trying to find out

Start with the question, because it keeps everything else in proportion.

You are almost never asking whether the code is good. That is not your call. Whether it is efficient or well structured is a developer’s judgment, and offering one costs you standing rather than earning it.

You are asking three much narrower things.

ExistsDoes the tracking call exist at all?
ValuesDoes it carry the values your specification asked for?
PlaceIs it in the place your specification asked for?

All three are answerable by reading rather than by understanding. You are matching text against a specification, not following logic. That distinction is the whole trick.

Five shapes worth recognising

Programming languages differ far less than they look, and the differences are mostly punctuation. Five shapes carry almost everything you need.

CallA name followed by brackets: sendEvent(...). Something is being done, and the name usually says what.
StringText in quotes. This is where your values live.
VariableA name with no quotes around it, standing in for a value decided elsewhere. This is the important one.
ConditionStarts with if. The code below it only runs sometimes.
CommentStarts with //. A note to people, ignored by the machine.

That is enough to read a tracking call. It is not enough to review one or to suggest a change, and those are different jobs you are not being asked to do.

The same call, in two languages

Here it is in Swift, which is iPhone. Two things happen: a list of values is built, then it is sent.

var xdmData : [String: Any] = ["eventType" : "SampleXDMEvent",
                              "sample": "data"]
let experienceEvent = ExperienceEvent(xdm: xdmData)
Edge.sendEvent(experienceEvent: experienceEvent)

Read it as a sentence. The first part builds a labelled list of values, and the words in quotes are yours: eventType is a field name from your schema, and the value beside it is what will arrive in the dataset. The last line sends it. Edge tells you which extension is sending, and sendEvent tells you what it is doing.

Now the same thing on Android, in Kotlin. The punctuation changes and nothing else does.

val xdmData = mutableMapOf<String, Any>()
xdmData["eventType"] = "SampleXDMEvent"
xdmData["sample"] = "data"
val experienceEvent = ExperienceEvent.Builder()
  .setXdmSchema(xdmData)
  .build()
Edge.sendEvent(experienceEvent)

Same three parts, in the same order. Values are collected under field names, an event is built from them, and the event is sent. Notice the words in quotes are identical to the Swift version, because those come from your schema rather than from the language.

The variable is where the faults hide

This is the most useful thing on this page. Look at what is not in quotes.

A value in quotes is fixed, and you can read it directly. A value that is a bare name is decided somewhere else, at the moment the code runs, and you cannot see it from the snippet at all.

xdmData["eventType"] = "commerce.purchases"   // fixed, and readable
xdmData["currencyCode"] = cart.currency       // decided elsewhere, invisible here

The second line might be perfect. It might also be empty on screens where the cart has not loaded, or lowercase where your schema expects uppercase, or missing for guest checkout. Nothing in the snippet tells you, and no amount of staring will.

So when you see a bare name where a value should be, you have found the one thing worth asking about: what is that when the app runs, and what is it when things go wrong? Then confirm the answer in Assurance, on a real phone, because that is the tool that shows the value rather than the intention.

Searching beats reading

Reading a snippet somebody chose to show you is the weak version. The strong version is finding out whether something exists at all.

A snippet answers whether one call is right. A search answers whether the call exists anywhere, which is a different and usually more urgent question.

You do not need access to the code yourself. You need to ask for the right search. Searching for sendEvent finds every place the app sends anything. Searching for a field name from your schema finds every place that field is filled in.

More usefully, it tells you whether that is one place or nine. A field set in one place is a field you can reason about. The same field set in nine places, by four people, over two years, is the explanation for a value that is right most of the time.

What not to do with this

Do not propose code changes. Reading four lines does not qualify anybody to edit them. An analytics person who arrives with a suggested fix has moved onto somebody else’s side of the line, and the developer now has to review your code as well as solve the problem. Where your job ends sets out that line in full.

Describe what you saw and what you expected. “The event fires on the confirmation screen but currencyCode arrives empty for guest checkout” is worth a great deal, and it takes no position on how to fix it.

That sentence is what reading code is for. Everything else on this page exists so you can write it with confidence.

What to do with a snippet in a ticket

FindThe field names and values in quotes, and check them against your specification. Misspelled field names are the most common fault and the easiest to see.
FindThe values that are not in quotes. Those are the ones no snippet can verify, so they are the ones worth a question.
AskFor a search rather than a snippet: how many places set this field? One place is a value you can trust. Nine places is the answer to a discrepancy you have not investigated yet.
ConfirmIn Assurance, on a real phone, before concluding anything. Code shows intention. Assurance shows what actually left the phone, and only one of those is evidence.
