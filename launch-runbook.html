amitdusane.com Launch Runbook

Twelve steps, in the order they happen. Nothing reaches the live site until step 7, and one step before it cannot be done afterwards.

Live branch main Work branch develop Expected pages 219 Deploy time ~2 min

Do not start before 05:30 IST

The learning section is dated 4 September. The build server runs on UTC, which is five and a half hours behind you, so until 05:30 your time it is still the 3rd over there. Build before then and Hugo treats all 116 sections as not yet published, drops them, and the site fills with “Coming soon” while reporting success.

After 05:30 IST this cannot happen. There is no other timing constraint.

STAGE 1

Get develop ready

Everything here is reversible and nothing is public. The live site is still the June version throughout.

1

Pull, and confirm nothing is half-finished

Makes sure we start from exactly what is on GitHub, with no stray edits left over.

git fetch origin
git status
Expect“up to date with origin/develop” and “nothing to commit, working tree clean”.
Stop ifanything is listed as modified. We look at it before going further.
2

Turn Google Analytics on

The tracking line is currently sealed inside a comment block, so the site ignores it. Removing the block lets it run. Property G-9817PZWN9H, already in the config.

  • File: layouts/partials/head.html, the block at lines 6–14
  • The wrapper goes; the tracking line inside it stays
Expectone line changed in one file.
3

Remove the temporary date override

This was added so testers could see pages dated 4 September before the 4th arrived. Today it arrives on its own, so the override comes out and the safety net it was suppressing comes back.

  • hugo.toml — the buildFuture = true line and its comment block
  • CLAUDE.md — the matching temporary block
4

Build, and check the numberThe gate

This one check has caught every silent failure on this project. A build can report success and still be missing a third of the site.

rm -rf amitdusane-site-complete/public
hugo --gc --source amitdusane-site-complete
Expect219 pages, and the tracking snippet present in the built HTML.
Stop ifit says 103. That is the date problem, and it means it is still the 3rd in UTC. Wait, then rebuild. Do not continue past this step.
5

Commit and push develop

Saves the two changes to GitHub. Still nothing live — pushing to develop publishes nothing.

Expecta clean working tree and develop up to date.
STAGE 2

Preserve version 1

One step, and it is the only one on this page that cannot be done afterwards.

6

Tag the current live site as v1.0Do first

Git keeps every version forever, but only while something points at it. Step 7 replaces main, which leaves the June site unpointed-at — and GitHub eventually deletes commits nothing points to. This tag is what pins it permanently, so you can browse or restore the June site any time.

git tag -a v1.0 730c59a -m "The June 2026 site, live until launch"
git push origin v1.0
Expectthe tag to appear under Tags on GitHub.
Stop ifthis fails. Everything after this depends on it.
STAGE 3

Go live

From here the public site changes. Reversible in about two minutes, but visible in the meantime.

7

Replace main with developPoint of no return

This is the launch. It is an overwrite rather than a merge, because the two branches never shared a starting point. It also joins them into one history, so every future launch is an ordinary, simple update.

git push origin develop:main --force-with-lease
Expectthe push to succeed and a build to start automatically.
8

Watch the deploy finish

GitHub builds the site and publishes it. Around two minutes.

  • GitHub → Actions tab → the run at the top
Expecta green tick.
Stop ifit fails. Read the error before touching anything — the old site is still up until the build succeeds.
9

Check the live site yourself

Five things, in this order. Each one has failed at some point during this project.

  • amitdusane.com loads, with both cards on the home page
  • /adobe-analytics-learning/ loads — this returned 404 by design until today
  • Open any section. No “Coming soon” anywhere
  • The byline reads Published: 4 Sep 2026
  • Google Analytics → Realtime shows your own visit
10

Tag the launch as v2.0

Names this version so you can find it later without hunting through commit IDs. From now on every push to main is preserved automatically — this tag just makes the milestone easy to reach.

git tag -a v2.0 -m "Adobe Analytics Learning launch"
git push origin v2.0
STAGE 4

Straight after launch

Same sitting. Leaving this to later is how the first week of data gets spoiled.

11

Turn Google Analytics back off on developSame day

Your staging copy is built from develop. With tracking left on there, every tester click lands in the same report as real visitors, and your launch-week numbers are wrong in a way you cannot separate out afterwards.

  • Put the comment wrapper back in head.html
  • Commit and push develop
Expectthe staging page to carry no tracking snippet; the live site keeps it.
12

Confirm the split is right

One last look, so you know the two sites are behaving differently on purpose.

  • Live site: tracking on, learning section published
  • Staging: tracking off, same content

If anything goes wrong after step 7

The June site goes back up within about two minutes:

git push origin 730c59a:main --force

Nothing is lost either way — the new version stays safe on develop, and v1.0 is tagged.

Deliberately not doing tomorrow

The RSS feed. It is genuinely missing, but it is new code that has never been built or tested. Adding a feature inside the launch window is how launches go wrong. It ships afterwards, or tonight if you want it tested first.

Making the tracking switch automatic. Steps 2 and 11 are a manual on/off that will repeat at every future launch. The site already has a guard that behaves differently on the live domain than on staging, and tracking could use the same trick — on by itself on amitdusane.com, off everywhere else. Worth doing, but after launch, not during.
